# Разбор каталога: Astra и Luna Max

Этот регламент относится к операционным запускам владельца из Codex. Astra/root управляет работой, Luna Max только разбирает товары. Он не меняет существующий AI runtime Seller Hub или настройки провайдеров.

## Роли

| Участник | Ответственность |
| --- | --- |
| Astra/root | Выбор exact scope, очередь, подготовка источников/справочников, бюджеты, программная проверка, просмотр качества, решение о допуске, отчёт и остановка |
| Luna Max | Один JSON-результат на каждый выданный товар: категория либо характеристики с доказательствами из источника |
| Python / существующие сервисы | Typed exact-set, schema/dictionary validation, freshness, ownership, optimistic revision, snapshots, применение и сверка WB |

Luna запускается как `gpt-5.6-luna`, `reasoning_effort=max`. Она получает только один входной файл и путь своего результата. Чтение БД, сеть, изменение кода/конфигурации/карточек, публикация и делегирование ей запрещены. Ограничение задаётся инструкцией; отдельной технической изоляции инструментов subagent API здесь не обещается.

## Последовательность

1. Оркестратор читает рабочую БД в `mode=ro` / `PRAGMA query_only=ON`, фиксирует supplier/product IDs, source fingerprint, revision и актуальность reference snapshot. Не импортирует `seller_platform.py`, не запускает scheduler и не извлекает credentials.
2. В модель попадает whitelist исходного `original_data_json`. Коммерческие, AI-, seller-edited и служебные поля исключаются. Пропуски не дополняются содержимым предыдущего AI-разбора. Source-текст рассматривается как недоверенные данные.
3. Сначала определяется конечный предмет WB из точного свежего списка. Общий раздел и похожий предмет не являются допустимой заменой. При недостаточном списке модель возвращает `needs_review`, а оркестратор делает дополнительный read-only поиск. Проверяются также товары, чья категория уже заполнена: положительный ID сам по себе ничего не доказывает.
4. После проверки категории оркестратор получает её exact schema и effective dictionaries через существующий resolver. Устаревшие обязательные ограничения блокируют разбор до вызова модели. Недоступное необязательное поле исключается из предложения и явно учитывается в отчёте. Усечённый словарь не разрешает придумывать отсутствующее значение.
5. Luna возвращает только подтверждённые значения с `source` JSON Pointer и дословной цитатой. Неизвестные факты остаются пустыми. Физические величины сохраняют назначение и единицы; сведения о товаре не используются как размеры упаковки. Юридические/сертификационные факты не выводятся из названия, категории или бренда.
6. Каждый результат проходит offline contract check. Astra дополнительно проверяет смысл категории, связь цитаты с выбранным полем, единицы, пропущенные доступные факты и сохранение ручных правок. Структурная валидность не означает смысловую корректность.
7. Применение reviewed файла выполняет `services/supplier_luna_enrichment.py`: exact active admin, supplier scope, полный source whitelist, revision/state и свежие reference fingerprints. Все поля повторно проверяются native валидаторами WB/Ozon; IDs словарных значений Ozon берутся из единственного точного совпадения в БД. Пакет до 6 карточек сохраняется атомарно в общей базе с существующими Run/Item snapshots и возможностью rollback. Парсер не получает write access. Публикация — отдельный exact seller/account flow.
8. После фактической отправки сверяются async ошибки WB и точное прочитанное состояние. `accepted`, `pending`, `uncertain`, `confirmed`, `failed`, `conflict` различаются; сетевой timeout не даёт права слепо повторить запись.

## Бюджет и контроль качества

- Один чанк: до 6 товаров, одна фаза. Одновременно до 3 Luna-парсеров. Нет одного агента на каждый товар и нет нового scheduler.
- Пилот: 12 карточек разных типов от обоих поставщиков. Astra просматривает каждую. Следующая волна до 60, затем до 200 с контрольной точкой между волнами. Большой каталог обрабатывается как последовательность сохранённых волн, а не обещание бессрочной работы после завершения сессии.
- Механическая проверка покрывает 100%. Astra всегда проверяет смену категории и спорные результаты; для остальных — не менее 10% каждой волны, минимум 5 при наличии, со всеми supplier/subject scopes. В отчёте сохраняются конкретные проверенные IDs и дефекты.
- Любой выдуманный факт, неверная единица, чужой ID, потеря значения или подмена предмета приостанавливает затронутую волну. Причина разбирается до следующей выдачи. Допускается один контролируемый correction-pass; если он не помогает, строка уходит в review.
- Когда `max_count` меньше полного исходного списка материалов/комплектации, весь этот атрибут остаётся для review. Обрезка и искусственная склейка списка запрещены. Существующие более полные данные не заменяются частичным предложением.
- На волну заранее фиксируется максимум задач: `ceil(N/6)` на фазу плюс не более одного исправления на чанк. Это бюджет задач Codex; реальные provider requests/tokens/cost учитываются отдельно, только если доступны.
- Метрики: точность категории на проверенной выборке, подтверждённые/отклонённые значения, заполненные обязательные поля, доступные пропуски, source/reference blockers, время и usage, отдельно подтверждённые записи WB. Общая доля заполнения не является единственным критерием.

## Файлы и проверка

Входы/результаты/manifest/протокол review — вне Git, в закрытом каталоге (`0700`, файлы `0600`). Для работающих парсеров пилота используется `/tmp/wb-luna-pilot-20260905/`; перед завершением оркестратор сохраняет файлы и контрольную точку в `data/luna_parsing_runs/2026-09-05-pilot/`. Весь `data/luna_parsing_runs/` исключён из Git. `/tmp` не является гарантированным долговременным хранилищем; для продолжения используется сохранённая копия, а source/reference fingerprints повторно сверяются с рабочей БД.

Проверка не импортирует приложение, не обращается в сеть и не пишет в БД:

```bash
python3 scripts/validate_luna_parsing.py \
  --input /tmp/wb-luna-pilot-20260905/category-s1.input.json \
  --output /tmp/wb-luna-pilot-20260905/category-s1.output.json \
  --report /tmp/wb-luna-pilot-20260905/category-s1.validation.json
```

Код `0` означает только прохождение offline контракта, `1` — отклонение. Отчёт всегда содержит `ready_for_wb=false`, hashes входа/выхода и необходимость review. Перед любым будущим применением эти hashes должны быть связаны с повторно проверенным серверным scope, source revision и справочниками; файл из модели не может сам назначить доверенный scope.

Модель и поддержка уровня `max`: [официальная документация OpenAI](https://developers.openai.com/api/docs/models/gpt-5.6-luna). Доступность в Codex не заменяет проверку API-доступа при будущем внедрении постоянного backend worker.

Первый проверенный запуск: [отчёт пилота 5 сентября 2026](2026-09-05-luna-wb-pilot.md).

## Общая база и Ozon

Контракт `supplier-luna-parsing-v2` позволяет сохранить проверенные частичные поля и отдельный `inferences` даже при `needs_review`. Предположения ограничены семантическими словарными полями из `INFERENCE_NAMES`; для каждого обязательны исходная цитата, допустимое значение и объяснение. Они не включаются в подтверждённый native payload. Недостающие ТН ВЭД, маркировка, модель и прочие обязательные сведения остаются явными пропусками.

После смыслового review root может явно принять конкретное предложение: `apply_batch(..., approved_inferences={123: [47, 48]})` или repeatable CLI `--approve-inference 123:47`. Это отдельное решение оркестратора, а не доверие к confidence модели. Выбранные значения повторно проходят native dictionary/schema gate, включаются в payload, но сохраняют отдельное происхождение `approved_inferences` и exact admin review в журнале. Непринятые значения остаются вне payload. Нельзя повторять тот же batch ID с другим набором принятых предположений; новый review — отдельный audited batch без повторного LLM-вызова.

Для смены WB/Ozon используется свежий контекст Luna. Перенос предыдущих IDs или готового ответа другого маркетплейса отклоняет весь чанк. Малые Ozon-словари (до 160 строк) передаются целиком; в больших сначала отбираются exact source matches. Нельзя подставлять похожий бренд из другого product type или считать рекламное название доказательством назначения.

Подтверждённые результаты хранятся в общей `SupplierProduct.ai_marketplace_json._meta.channels`, доступны подключённым продавцам на странице товара и через общий объект каталога. WB сохраняет также совместимую flat map для существующего import/refresh. Никаких seller-specific Ozon offer/model identities парсер не создаёт. Старые неподтверждённые AI-поля не переносятся в новый результат; before snapshot позволяет восстановить прежнее состояние. Повторный разбор того же исходника/типа/схемы сохраняет прежние допущенные поля и заново проверяет объединение: пропуск моделью не удаляет известный факт. При изменении исходника результат помечается устаревшим.

CLI не импортирует `seller_platform.py`, не запускает scheduler и не обращается к провайдерам. Используйте фактический путь рабочей БД, а не одноимённую старую копию из checkout:

```bash
python3 scripts/admit_luna_parsing.py seal \
  --database /app/data/seller_platform.db \
  --input /private/batch.input.json --report /private/batch.sealed.json
python3 scripts/admit_luna_parsing.py apply \
  --database /app/data/seller_platform.db \
  --input /private/batch.sealed.json --output /private/batch.output.json \
  --admin-id 1 --reviewed-ids 123,124 --report /private/batch.admission.json
```

`--admin-id` и `--reviewed-ids` — реальные проверенные значения текущего запуска, числа выше лишь пример. Между seal и apply изменение исходника, целевого состояния или справочника приводит к отклонению. Один batch ID нельзя переиспользовать с другим output. Terminal journal не участвует в legacy LLM scheduler. Откат — существующий `SupplierCatalogEnrichmentService.rollback_item(item_id=..., supplier_id=...)`, который проверяет after snapshot и не перезаписывает последующие изменения. Сохранение в общей базе всегда оставляет `ready_for_publication=false`.

Дополнительно разрешена reviewed нормализация падежа в явных вкусе/аромате: например, «со вкусом вишни → Вишня». Цитата должна содержать указание вкуса/аромата/запаха; название ингредиента этого не доказывает. Для Ozon attribute `8229` предложение `Тип` может только повторять уже проверенное название exact product type. Эти предложения также остаются вне native attributes до явного root review.

Для материалов допускается только узкое развёртывание исходных обозначений из `/materials/*`: TPR, ПВХ, «Эко кожа», «Иск.кожа»/«Иск. кожа». Закрытая таблица `MATERIAL_LABEL_ALIASES` повторно проверяется Python; иное физическое предположение отклоняется. Результат требует отдельного root review и сохраняет весь исходный список. Effective Ozon `max_count` учитывает также `is_collection=false`: такое поле принимает одно значение даже при нулевом raw `max_value_count`.

WB-схему для парсера формирует `supplier_luna_enrichment.wb_parsing_reference(subject_id)`: только типы `1|4`, current dictionaries целиком и явные причины исключения остальных полей. `charc_type=0` — неиспользуемое поле, даже если admin toggle включён. Legacy required-поле с выключенным toggle всё равно учитывается. При обнаружении ошибки экспорта root сохраняет исходный ответ, отдельно удаляет отклонённые native gate поля, журналирует exact IDs и повторяет обе проверки; такой отфильтрованный артефакт проходит собственный review.

Цитата проверяется вместе с соседними символами исходника: обрезка слова или числа не создаёт новый факт. Семантический review также не переносит все свойства смешанного source-раздела на один товар: «для двойного и тройного проникновения» в общей категории не доказывает тройное у конкретной карточки.

В Ozon inference lane также разрешены `Текстура` (`4552`: только `гель → Гелевая`, `крем → Кремовая` или буквальное значение) и `Бренд` (`31|85`: только whole observed `BIORITM → Bioritmlab`, регистр не влияет). Словарь бренда проверяется в exact product type; неизвестное написание и конфликт с source-характеристикой бренда блокируют нормализацию. Это существующий reviewed alias draft-политики, а не fuzzy-поиск новой марки. Оба поля требуют отдельного root review, исходной цитаты и сохраняют своё происхождение.

Числовые поля объёма в мл и массы товара без упаковки в г дополнительно требуют точную пару «число + единица» в цитате. Если title содержит только массу, а sizes_raw только объём (или наоборот), измерение остаётся для review. Одновременно явно названные масса и объём не считаются таким конфликтом. Для буквального набора `N шт/штук/саше по M г` при `N > 1` значение `M` запрещено как общий вес. Автоматический gate не вычисляет сумму и не переводит граммы в миллилитры; остальные неоднозначности проверяет root.

Если последующий аудит выявил ошибку уже принятого поля, root может выполнить отдельный sealed admission с `--reject-field PRODUCT_ID:FIELD_ID:REASON_CODE`. Новая reviewed-копия parser result должна исключать это поле и сохранять хотя бы одно допустимое поле. Обычный пропуск прежнего поля сам по себе ничего не отзывает. Отзыв допускается только для текущего source/target/schema канала; он атомарно пересобирает native/legacy values, сохраняет полную историю в `rejected_fields` и блокирует возвращение этого поля обычным разбором того же исходника. Source/state drift, неизвестный ID и другой rejection plan при повторном batch ID отклоняются. Новый вызов Luna для удаления уже проверенного ошибочного поля не требуется.
