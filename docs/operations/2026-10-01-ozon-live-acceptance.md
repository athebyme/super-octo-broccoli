# Ozon и остаточная UX-приёмка: итог r7 и внешние ограничения

Отчёт разделяет проверенную реализацию и доказательства внешних эффектов. `PASSED` относится только к указанному scope и receipt; синтетическая приёмка не доказывает реальное действие маркетплейса. `NOT TESTED` означает, что действие или внешний результат не проверялись. `BLOCKED` указывает конкретное препятствие следующему шагу. ## Live reads и фактические границы

В phases 1–4 выполнено 16 ограниченных API reads: 13 ответов HTTP 200, один 404 и два 403; retries, redirects, provider writes и LLM calls не выполнялись. Собственные offer/product совпали по доступным наблюдениям; в ответах prices/stocks отсутствовал SKU, что ограничивает доказательство идентичности по этим lanes. Один exact task-status read вернул 404: исход неизвестен, повторной операции не было. Одиночный bounded photo cache-hit вернул JPEG 1200×1200 (103974 bytes), но это не холодная загрузка и не публикация/преобразование Ozon. За один завершённый UTC-день orders/returns дали 0 строк с `has_next=false`, finance — одну строку; это не утверждение об отсутствии заказов за всю историю. Reviews/questions дали 403, причины неизвестны.

Отдельная buyer-price проверка также получила 403. Ни этот отказ, ни grants из `/v1/roles` не объясняют причину доступа. Blind probes не повторялись. `old_price`, seller price или их разницу нельзя выдавать за buyer price или скидку Ozon.

Read-only Ozon-каталоговый отбор ранее прошёл три страницы и нашёл 258 строк в применённом фильтре; 255 не представимы текущим контрактом из-за множественных barcode. Исчерпание этого фильтра не является полным обходом каталога. Исправленный r7 scan отдельного диагностического helper (не изменения runtime r7) исчерпал 34 страницы и 4 129 собственных linked/available строк. После исправления SQL projection alias он запустил native validator для 3 312 строк: 0 publishable в проверенном scope. У 3 286 ошибок превышения `max_value_count` все значения различны: 2 893 группы — 5 при лимите 4, две — 6 при лимите 4, 391 — 2 при лимите 1; точных дубликатов — 0, случаев с max=0 — 0. Ещё два случая остановлены source/operation guards. Required-field gaps: attribute 22232 отсутствует у 3 310, 23536 у 2 141, 8229 у 3 311 строк. Отдельный изолированный source-presence scan проверил все 177 required-only источников: 164 имеют exact WB FK/owner/nmID, у 141 найден один явный 10-digit ASCII код ТН ВЭД только в `Product.characteristics_json`; конфликтов — 0, явных marking literals — 0. Эта кэшированная projection может содержать исходящий payload; generic `last_sync` не доказывает live-WB наблюдения. Значения и IDs остались в private receipt. Свежий exact-WB read, текущий Ozon dictionary match и безопасный draft-create путь ещё проверяются. Это не обход всего каталога и не доказательство глобального отсутствия подходящих товаров. Ни provider/API writes, ни автоматическая классификация или crop не выполнялись; live pilot пока без записей.

### WB-EDIT-02: граница обычного admin-route для schema refresh

В r7 есть existing route `POST /admin/marketplaces/categories/<category_id>/sync_characteristics`: он загружает ровно одну локальную WB `MarketplaceCategory` и вызывает обычный сервис/клиент для её текущего `subject_id`. Форма получает CSRF через обычный category detail GET. Это точечный refresh глобального reference cache, не seller-private product API; он может записать локальную schema cache и при TNVED вызвать дополнительный read. Route использует штатные limiter/retry/redirect/TLS свойства приложения. Его нельзя считать read-only peek или обещать ровно один physical provider request.

Root выполнил read-only preflight точного runtime admin identity: только одна existing user совпала с runtime username и email, активна, не заблокирована, уже имеет admin flag, а хэш совпал с runtime password. Startup `_ensure_admin_from_env()` и promotion/fallback не вызывались. Текущий live target подтвердил 32 собственных WB products с точным именем `Свечи эротик`, один положительный subject ID и одну существующую available WB category с тем же subject/name. Проверка current scope установила точную identity; причина более раннего `subject not found` остаётся неизвестной.

По уже предоставленной владельцем авторизации root выполнил один обычный HTTPS flow: GET login с CSRF, credential POST с ротацией cookie, GET category detail с новой CSRF, один POST existing sync route, затем category readback. Было ровно 1 normal-login POST и 1 category POST; обе операции вернули ожидаемый HTTP 302, readback category page — 200. В целевой локальной schema cache теперь `success`, 32 характеристики, version 5→6; предыдущий snapshot был от 30.09.2026 18:09, новый свежий snapshot — 02.10.2026 00:58:08 UTC. Обновился только локальный глобальный reference cache; WB card writes/provider writes — 0. Успешный login также меняет обычные локальные auth/last-login metadata пользователя. Физическое число WB provider reads не измерялось: применяются штатные server retries и возможен условный TNVED read.

Предыдущий r2 вызов получил настоящий HTTP 302 на login, но локально сообщил `TooManyRedirects` из-за `requests.Session.max_redirects=0`; bounded server log evidence подтвердил 1 login POST и 0 category POST, без сохранения/вывода raw logs. Новый временный r3 helper убрал этот клиентский дефект, сохранив явное `allow_redirects=False` и отсутствие transport retries. До live вызова его реальные `requests.Session` cookie/CSRF/redirect flow прошёл 24 offline mock-adapter tests: r2 302 failure воспроизведён; r3 проверил login→category POST→readback с нулём socket/provider calls. Live r3 прошёл один authorized refresh. Массовый browser workflow WB editor, card edits/history и card readback не запускались; они остаются **NOT TESTED**.

Точный текущий официальный write contract для inbox replies и shipping/labels (W9/P10) не получен: официальные страницы перенаправлялись по кругу; просмотр 29 официальных `ozontech` GitHub repositories не обнаружил точной Seller API спецификации для этих операций. Community Postman collection не считается авторитетным контрактом. Ответы покупателям и отправка данных отгрузки поэтому остаются **не реализованы**; локальные reply drafts и read-only данные не являются этими функциями.

Sanitized r7 known-key audit использовал 20 private records с 14 distinct values; совпадений — 0. Его generic pattern scan отметил 994 строки-кандидата. Исторический r6 audit отдельно проверял 14 известных значений и показывал 992 generic candidates; эти счётчики нельзя объединять или переносить между выпусками. Generic candidates не подтверждают секрет и не доказывают отсутствие любых исторических значений. Аудиты не покрывают неизвестные секреты, недостижимые Git objects или unfetched refs; свежий аудит после fetch и r7 artifact commit `cd7df65` также завершился с 0 known matches и 994 generic candidates; последующие result-only commits требуют повторной проверки перед завершением. Test credentials в evidence не копировались; локальные файлы имели права 0600, каталог — 0700. Ключи/хэши, реальные offer/product/SKU IDs, raw API bodies и buyer data не включены; bodies и buyer data не сохранялись.

## Продолжение 02.10: выбранная карточка и live WB browser

Свежий exact собственный WB card read через обычный WB-клиент дал один HTTP 200 без повторов, redirect или записи карточки. Точный seller/FK/nmID/vendor/current-Product subject совпал. Сохранённый ImportedProduct subject отличается от текущего WB Product: это устаревшая локальная классификация, она не менялась и не подменяла текущий source identity. В текущей WB-схеме ТН ВЭД — необязательное поле, но один явный наблюдённый код есть; requiredness Ozon проверяется отдельно. Directory `isKiz=true`, card `needKiz=false` и `kizMarked=false` остаются различными наблюдениями, юридическая классификация из них не выводится. Ключ использовался только в памяти. [Свежий source receipt](../design/ozon-live-acceptance-artifacts-2026-10-01/fresh-wb-source-r4.json).

Для выбранной карточки свежий официальный Ozon словарь содержит ровно два доступных значения одного кода, чьи полные описания различаются одной конечной ASCII-точкой. Root явно выбрал существующую строку без точки для одной карточки; автоматическое разрешение неоднозначного кода и общий default не использовались. Отдельная проверка на восстановленной read-only базе без сети подтвердила эту пару, exact значение `Тип` и native validation: publishable=true, ошибок 0. Изменились только simple attributes (24→26), остальные шесть блоков сохранились точно; все семь эффективных блоков и canonical payload совпали с рассмотренным предложением. Baseline simple-attribute row order допустимо меняется в прежнем merge, но значения, их порядок внутри атрибута и full-state fingerprint сохраняются. Сохранённых черновиков, link mutations, credential decryptions и provider calls в этой проверке — 0. Это проверенная локальная возможность подготовить исправление, не выполненное обновление Ozon. [Native receipt](../design/ozon-live-acceptance-artifacts-2026-10-01/explicit-manual-native-r3.json).

Тот же замороженный R3 helper прошёл с ограниченным private 64 MiB tmpfs при сохранённых read-only app/DB и `--network none`; root offline suite — 12/12. Эти остановки относятся к диагностическому окружению, не к provider-ошибкам.
