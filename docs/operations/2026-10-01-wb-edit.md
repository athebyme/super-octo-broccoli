# WB editor safety and verification — 2026-10-01

## Implemented behavior

The `/products` list and bulk editor now share one seller-scoped filter builder. Selection stores exact local `Product.id` values under the current seller, WB account, and filter fingerprint. Sorting and pagination preserve that set; changing filters or account clears it. “All filtered” resolves the same filters on the server, is an explicit action, and is capped at 200 internal Seller Hub products. A larger result is rejected as a whole and asks the seller to narrow the scope. This is an application safety cap, not a WB API limit. The browser receives a signed selection token rather than a catalog result set. Resolver and editor reject malformed, repeated, foreign, or filter-mismatched IDs before any provider client is used.

The editor return path accepts only a local `/products` URL with supported, unique query keys. It carries the search, filters, sort, order, page, and page size through the bulk flow. Invalid return paths fall back to `/products`.

Bulk apply requires a local preview. Preview reports selected, eligible, changed, skipped, and invalid counts, lists exact subject groups and old-to-new field values, and names the seller/WB account and channel. It does not create a WB client or send provider traffic. Empty, invalid, and no-op reviews cannot be applied. Apply rechecks the signed review identity, local product/schema revisions, and shared WB characteristic validation before I/O. A durable unique review key is committed in `BulkEditHistory` before provider I/O; a replay or concurrent duplicate returns the same seller-owned history and makes no second provider attempt, including after an ambiguous timeout.

The same local review and durable one-use token now covers the existing manual brand, append-description, replace-description, and keyword actions. Brand and description previews name Wildberries as their provider channel. Keyword changes are explicitly labeled as Seller Hub local-only and bypass WB client construction. Empty and unchanged operations have no apply token. A manual change submitted alongside one or more AI actions is stopped with an explicit message and no write; AI-only actions keep their existing route and are a separate user action. Their generated values are not claimed as previewed before the AI step produces them.

Single-product edit reads characteristics from the local authoritative WB category cache. It permits supported missing characteristics to be filled while size/SKU identity remains read-only. Country values use the shared dictionary; numeric, unit, and multi-value inputs use the shared validator. Stale schema is displayed as unavailable and cannot be applied. Name-based `/api/characteristics/<object_name>` compatibility now resolves only through exact, seller-owned Product rows and their exact `subject_id`; ambiguity, missing mapping, or stale schema fails closed. The by-subject and multi-category endpoints likewise require a subject backed by a product owned by the current seller and return local schema only. Existing response aliases are retained for the old UI contract.

## Category evidence

The bounded, read-only local metadata inspection observed 32 products named “Свечи эротик”, all with `subjectID=5880`; cached category 5880 was enabled, a leaf, and had a successful schema sync at `2026-09-30 18:09:54.924237`, with 32 of 32 characteristics. “Мастурбаторы мужские” had 605 local products at `subjectID=5070`, with 31 of 31 cached characteristics. No provider category lookup or write was performed.

The former name resolver's implementation could fall back to the first returned subject when it did not find an exact name match. The historical provider response for the affected request was not retained, so that behavior is a risk found in code, not a proven explanation for the original “subject not found” report. The editor now uses exact observed subject IDs and a fresh local schema; it does not remap one category to another.
