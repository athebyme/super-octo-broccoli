# Админские compliance-дефолты Ozon: ТН ВЭД и признак маркировки

Дата: 2026-07-25
Статус: дизайн согласован, реализация не начата

## Задача

Каждая новая Ozon-карточка блокируется ровно двумя обязательными атрибутами:

- `22232` «ТН ВЭД коды ЕАЭС» — String, type-scoped словарь;
- `23536` «Нужен код маркировки» — Boolean, без словаря.

Измерено на живой БД 2026-07-25: черновики 3–7 и вновь созданный №9 блокируются
одним и тем же набором, `required_supplied = 3/5`. Все прочие блоки полноты
(контент, медиа, габариты, цена, штрихкод, бренд) проходят.

Цель — сделать оба поля автоматическими «под капотом», не превращая систему в
источник compliance-догадок.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Кто решает по ТН ВЭД | Админ платформы, значение общее для всех продавцов |
| Ключ хранения | Ozon product type |
| Что хранится | Строка кода, не `dictionary_value_id` |
| Как получается маркировка | Выводится из ТН ВЭД по версионированному нормативному реестру |
| Охват | Новые черновики молча; существующие — отдельным подтверждаемым прогоном |

### Принятое юридическое следствие

Выбран админский уровень решения, общий для всех продавцов. Это означает, что
точность таможенной классификации берёт на себя платформа, а не продавец.
Решение принято владельцем продукта осознанно; альтернатива (решение продавца в
его собственном scope) была предложена и отклонена. Каждое значение хранит
автора, дату и обязательное обоснование — ответственность персонифицирована
внутри платформы.

### Почему ключ — Ozon product type, а не категория поставщика

Словарь ТН ВЭД принадлежит `MarketplaceAttributeDefinition`, который привязан к
`product_type_id` (для типа 1609 «Мастурбатор» — 115 доступных значений).
`AGENTS.md` запрещает переносить `dictionary_value_id` между attribute/type
scopes. Ключ по типу делает scope значения и scope словаря одинаковыми.

### Почему хранится строка кода, а не ID значения

`external_value_id` может смениться или исчезнуть при пересинхронизации словаря.
Код переживает ресинк и является тем, что фактически решил человек. Резолв кода
в ID выполняется на каждом применении в свежем type-scoped словаре — ровно так
же, как это уже делает экран массовой починки.

## Объём работ

47 Ozon-типов реально задействованы (есть listing, draft или mapping), они
покрывают 7 471 листинг. 11 типов покрывают 80 % каталога. Заполнение админом
реалистично как разовая работа на один экран.

## Модель данных

Три новые admin-owned таблицы.

### `OzonComplianceDefault`

Решение по ТН ВЭД, одно активное на тип.

```
id
marketplace_id        FK marketplaces
product_type_id       FK marketplace_product_types
tnved_code            String(20)    -- нормализованная строка, только цифры
tnved_display         String(500)   -- наблюдённый display на момент решения, для аудита
status                active | retired
decided_by_user_id    FK users
decided_at            DateTime
rationale             Text          -- обязательно
dictionary_version    Integer       -- values_version словаря на момент решения
dictionary_hash       String(64)
version               Integer       -- optimistic
created_at, updated_at
```

Partial UNIQUE `(marketplace_id, product_type_id)` где `status='active'`.

`tnved_display` — только для аудита и отображения истории. В payload Ozon он
никогда не попадает: display берётся из свежего словаря при резолве.

### `OzonMarkingRegistryVersion`

```
id
label                 String(200)   -- напр. "ПП РФ, ред. на 2026-07-01"
is_complete           Boolean       -- перечень объявлен исчерпывающим
declared_by_user_id   FK users
declared_at           DateTime
rule_count            Integer
checksum              String(64)
status                active | superseded
created_at, updated_at
```

Partial UNIQUE где `status='active'` — активная версия ровно одна.

### `OzonMarkingRule`

```
id
registry_version_id   FK OzonMarkingRegistryVersion
code_prefix           String(20)    -- 2..10 цифр
normative_ref         String(300)
valid_from            Date
note                  Text
```

UNIQUE `(registry_version_id, code_prefix)`.

## Правило вывода маркировки

```
код ТН ВЭД → нормализация (только цифры)
→ самое длинное совпадение code_prefix среди правил активной версии
   ├─ совпадение найдено                 → requires_marking = true
   ├─ не найдено, is_complete = true      → requires_marking = false
   └─ не найдено, is_complete = false     → ответа нет (fail-closed)
```

Постановления о маркировке пишутся как исчерпывающие перечни групп кодов, часто
4-значными префиксами. Longest-prefix — способ читать такой перечень, а не
эвристика. Вывод «не в перечне ⇒ не маркируется» допустим только если перечень
объявлен полным, поэтому `is_complete` вынесен в отдельное явное утверждение
человека: оно делается один раз на всю систему, подписано автором и датой.

Override маркировки на уровне типа намеренно отсутствует. Если админ считает,
что тип маркируется вопреки реестру, он правит реестр. Один источник истины.

## Резолвер

`services/ozon_compliance_defaults.py` — чистый слой: SQL и строки, без
provider-вызовов и без LLM.

```
resolve_tnved(product_type_id)
  -> {code, display, external_value_id, evidence} | None

resolve_marking(tnved_code)
  -> True | False | None

resolve_type_defaults(product_type_id)
  -> {tnved, marking, unresolved: [...], evidence: {...}}
```

`resolve_tnved` обязан:

1. взять активный `OzonComplianceDefault` для типа;
2. найти `MarketplaceAttributeDefinition(product_type_id, external_attribute_id=22232)`;
3. потребовать `is_available` и `OzonReferenceService.dictionary_is_fresh(defn)`;
4. найти в `MarketplaceAttributeValue` строку, чей код точно равен сохранённому;
5. вернуть результат только при ровно одном совпадении; при нуле или более чем
   одном — `None` и запись в `unresolved`.

Правило разбора значения словаря: наблюдённая форма —
`"3307900008 - Косметические или туалетные средства, ..."`. Кодом считается
непрерывная ведущая последовательность цифр значения; всё, что после неё,
игнорируется при сравнении. Значение без ведущих цифр кандидатом не является.
Сравнение строгое посимвольное после нормализации обеих сторон до цифр —
никакого префиксного или fuzzy-совпадения на этом шаге (префиксы используются
только в реестре маркировки, это другой механизм).

## Точка применения

Порядок сборки черновика: source-рецепты → **compliance-слой** → валидация.

Слой применяется **не внутри** `_apply_source_recipes`. Инвариант «Маркировка и
ТН ВЭД никогда не выводятся из этих рецептов» сохраняется без изменений: рецепты
выводят значения из наблюдённых фактов товара, и это по-прежнему запрещено.
Админский дефолт не является выводом из фактов — это применение зафиксированного
человеческого решения, поэтому он живёт в отдельном слое с отдельным provenance.

Правила слоя:

- заполняет только пустые атрибуты;
- seller-edited значение не перезаписывается никогда;
- Boolean-маркировка пишется строкой `"true"` / `"false"`. Форма подтверждена по
  реальному черновику того же кабинета: атрибут `9070` («признак 18+», тоже
  `data_type=Boolean`) хранится как `{"attribute_id": "9070", "values":
  [{"value": "true"}]}`. Реализация обязана закрепить это тестом, а не
  предположением: если у `23536` наблюдается другая форма — приоритет у
  наблюдённой;
- provenance на каждый заполненный атрибут: `source=admin_compliance_default`,
  `default_id`, `registry_version_id`, `dictionary_version`;
- при неудачном резолве не ставится ничего, черновик остаётся `blocked` с явной
  причиной.

## Fail-closed матрица

| Ситуация | Поведение |
|---|---|
| Нет активного решения для типа | Не ставим. `blocked`, причина с номером типа |
| Словарь типа несвежий | Не ставим. `ozon_reference_stale` |
| Код не найден в словаре | Не ставим. Причина содержит код |
| Код найден более одного раза | Не ставим. Причина содержит код |
| Активного реестра маркировки нет | ТН ВЭД ставим, маркировку — нет |
| Реестр не полный, кода нет в перечне | Маркировку не ставим |
| Продавец уже заполнил поле | Не трогаем |

## Админский интерфейс

`/admin/ozon/compliance`, admin-only, токены «Тёплой редакции», обе темы, только
существующие `.sh-*` компоненты.

**Вкладка «Типы».** Список задействованных типов, отсортированный по числу
листингов — то есть по влиянию. Колонки: тип, листингов, черновиков, код ТН ВЭД,
маркировка с указанием источника вывода, автор и дата решения. Строка без
решения помечена как блокер с числом карточек, которые она держит. Выбор кода —
поиск по локальному type-scoped словарю без обращений к Ozon; рядом read-only
подсказки из `ozon_compliance_suggestions`. Поле обоснования обязательно.

**Вкладка «Реестр маркировки».** Активная версия, её правила, загрузка новой
версии, чекбокс «перечень исчерпывающий» с отдельным подтверждением, активация.
Перед активацией показывается diff: сколько типов поменяют вычисленный флаг.

## Охват существующих карточек

Новые черновики получают значения молча в слое применения.

Существующие — отдельная кнопка «Применить к существующим». Её точный scope:
неархивные `MarketplaceProductDraft` с `product_type_id`, равным типу текущего
решения, у которых соответствующий атрибут пуст и по которым нет активной
`MarketplaceOperation`. Черновики с активной операцией и с уже заполненным
продавцом значением пропускаются и показываются отдельным счётчиком. Прогон
bounded, обновляет только локальные черновики и выставляет `ready_to_retry`;
provider write не выполняется. Дальше используется существующий mass-upload с
явным подтверждением записи.

Смена админского кода не запускает автоматический write в Ozon ни при каких
условиях.

## Миграция

`migrations/migrate_add_ozon_compliance_defaults.py` — идемпотентная, создаёт три
таблицы и partial unique индексы, проверяет наличие таблиц и колонок, безопасна
при повторном запуске. Подключается fail-fast в `docker-entrypoint.sh` и в
comprehensive runner после `migrate_add_ozon_references.py`.

Backfill отсутствует: существующие черновики не изменяются молча.

## Сопутствующий фикс

`services/ozon_compliance_suggestions.py` не распознаёт кириллические
аббревиатуры материалов «ТПЭ» и «ТПР»: регексы знают латинские `tpr|tpe` и
кириллические `резин*|эластомер*|термопласт*`, но не кириллическое сокращение.
Проверено на живой карточке — `rubber_like=false`, `plastic_like=false` при
`material_label="ТПЭ"`, в результате подсказчик возвращает ноль кандидатов из 115
значений словаря. Фикс входит в тот же объём работ, потому что админский экран
опирается на эти подсказки.

## Тесты

- **Резолвер ТН ВЭД:** точное совпадение; отсутствие решения; два совпадения в
  словаре; несвежий словарь; `retired` решение.
- **Маркировка:** longest-prefix при вложенных префиксах; полный реестр и код вне
  перечня; неполный реестр; нормализация кода; отсутствие активной версии.
- **Слой применения:** не перезаписывает seller value; ничего не ставит при
  unresolved; корректный provenance; Boolean-форма значения.
- **Админ-роуты:** доступ только админу; optimistic `version`; обязательное
  обоснование; отклонение чужого `dictionary_value_id`.
- **Миграция:** идемпотентность при повторном запуске.
- **E2E:** черновик №9 (тип 1609) становится `publishable` после появления
  админского решения и активного реестра.

## Обновление AGENTS.md

Запрет на вывод compliance-фактов из рецептов и из consensus по опубликованным
карточкам сохраняется дословно. Добавляется явно очерченное исключение:
единственный допустимый источник ТН ВЭД — активное админское решение,
привязанное к Ozon product type; единственный допустимый источник признака
маркировки — активная версия нормативного реестра, применённая к этому коду.
Оба источника обязаны иметь автора, дату и версию, а результат — provenance в
черновике.
