# Качество карточек v2: честный скоринг, очередь исправлений, ИИ-handoff

Дата: 2026-07-13. Ветка: `feature/card-quality-rating`.

## Проблема

Текущий Quality Score меряет «наличие», а не качество: 8 любых фото, 10 любых
характеристик, 400 символов описания и заполненные бренд/штрихкод/цена/категория
дают 70+ баллов. Итог на реальном каталоге: «слабых» 4, «требуют внимания» 62 из
~9900 карточек — цифра кратно занижена. Средний бакет (3267 карточек) вообще не
попадает во флоу исправления. Карточки без WB-рейтинга (нет продаж) не считаются
слабыми, хотя отсутствие продаж — сигнал. Кнопки «Улучшить»/«AI-анализ» создают
задачи legacy-агентам (card-doctor, photo-optimizer, seo-writer…), которые в
актуальном рантайме офлайн.

## Решение (4 блока)

1. **Скорер v2** — контент-слой становится глубже и жёстче, добавляется
   поведенческий слой из воронки продаж WB (без новых API-запросов).
2. **Дашборд-виджет** — «N карточек теряют продажи» + чипы причин со счётчиками,
   каждый чип — ссылка на отфильтрованную очередь; спарклайн тренда среднего скора.
3. **Раздел /card-quality** — одна очередь исправлений с фильтрами по причинам,
   сортировкой по эффекту фикса и массовыми действиями.
4. **ИИ-handoff** — «Исправить с ИИ» передаёт выбранные карточки в единый
   чат-orchestrator через существующие endpoints чата; legacy-агенты из раздела
   убираются.

## 1. Скорер v2 (`services/card_quality_scorer.py`)

### Контент-слой

Изменения измерений (веса пересматриваются, сумма = 100):

| Измерение       | Вес | v2-логика |
|-----------------|-----|-----------|
| characteristics | 25  | Доля заполненных от доступных в категории WB: `sub = 100 * filled_weighted / available_weighted`, обязательные хар-ки весят ×3 против опциональных. Fallback: если конфига категории нет — старая шкала count×10, но с потолком 70 (без конфига нельзя подтвердить полноту). |
| photos          | 20  | `<5` фото — не более 40 баллов; 0 фото — 0. Шкала до 10 фото → 100. |
| description     | 20  | Длина (100% на 600+ символов) × штрафы: дубликат описания внутри каталога продавца (одинаковый текст у 3+ карточек) — ×0.4; менее 15 уникальных значимых слов — ×0.6. |
| title           | 15  | Длина 25–60 — база 100; штрафы: <4 значимых слов — −30; повтор слова 3+ раз — −20; сплошной CAPS — −20; >60 символов — 50. |
| brand           | 8   | Как раньше (наличие). |
| barcodes        | 6   | Как раньше (наличие). |
| price           | 3   | Как раньше (наличие). |
| category        | 3   | Как раньше (наличие subject_id). |

Кэш конфигов категорий: таблица `wb_subject_charcs_cache`
(`subject_id` PK, `charcs_json`, `fetched_at`), TTL 7 дней. Заполняется лениво
во время синка рейтингов (по уникальным subject_id активных карточек, через
`get_card_characteristics_config`); при недоступности WB скорер деградирует в
fallback и не блокирует пересчёт.

### Поведенческий слой

`sync_card_ratings_for_seller` уже получает полный ответ
`/api/analytics/v3/sales-funnel/products`, но парсит только рейтинги. Расширяем
парсер (defensive, все поля опциональны) и сохраняем в `Product`:

- `wb_views_30d` (int) — openCard за 30 дней;
- `wb_orders_30d` (int);
- `wb_cart_conv` (float, %) — конверсия просмотр→корзина;
- `wb_order_conv` (float, %) — корзина→заказ;
- `wb_buyout_rate` (float, %) — выкуп;
- `funnel_checked_at` (datetime).

Ноль дополнительных API-запросов; лимит 3 req/min не затрагивается.

### Причины (`attention_reasons`)

Типизированный набор флагов, вычисляется при каждом пересчёте скора:

| Код               | Условие (константы в скорере) |
|-------------------|-------------------------------|
| `few_photos`      | фото < 5 |
| `weak_chars`      | sub-балл characteristics < 60 |
| `weak_description`| sub-балл description < 60 |
| `weak_title`      | sub-балл title < 60 |
| `no_views`        | funnel есть и `wb_views_30d` < 30 |
| `low_cart_conv`   | `wb_views_30d` ≥ 100 и `wb_cart_conv` < 4.0 |
| `low_buyout`      | `wb_orders_30d` ≥ 5 и `wb_buyout_rate` < 30.0 |
| `low_rating`      | `nm_rating` < 6 или `wb_feedback_rating` < 4 |
| `no_sales_signal` | `nm_rating is None` и (`wb_views_30d` is None или 0) |

«Требует внимания» = список причин непуст. `is_weak()` v1 удаляется вместе с
порогами `WEAK_*`; все вызовы переводятся на причины.

### Приоритет фикса (`quality_impact`)

`quality_impact = Σ weight_i × (100 − sub_i) / 100` по контент-измерениям
(потенциальный прирост скора) + поведенческие бусты: `no_views` +10,
`low_cart_conv` +8, `low_buyout` +5, `low_rating` +5. Хранится в
`Product.quality_impact` для SQL-сортировки очереди.

### Хранение

Новые колонки `Product`: 6 полей воронки (выше), `attention_reasons`
(TEXT, CSV-список кодов — фильтрация `LIKE '%code%'`, объёмы ~10k строк для
SQLite приемлемы), `quality_impact` (FLOAT). `quality_breakdown_json`
расширяется полем `reasons` для UI-детали.

`compute_quality_summary` дополнительно возвращает `reason_counts`
(один проход по строкам, существующий TTL-кэш 60с сохраняется) и
`trend` — средний quality_score по дням за 30 дней из `CardRatingHistory`.

## 2. Дашборд-виджет (`templates/dashboard.html`)

Заменяет текущий блок `.dash-quality`, использует расширенный
`/api/card-quality/summary`:

- Заголовок-цифра: `need_attention` + «карточек теряют продажи».
- Чипы топ-4 причин по счётчику: `📷 Мало фото · 118` → ссылка
  `/card-quality?reason=few_photos`. Порядок — по убыванию count, нулевые не
  показываются.
- Спарклайн (inline SVG, без библиотек) тренда среднего скора за 30 дней +
  текущее значение.
- Полоска распределения слабые/средние/хорошие остаётся, сегменты становятся
  ссылками (`?bucket=poor|average|good`).
- Обе темы через существующие токены; hardcoded `#ece9e4` в виджете заменяется
  на токен.

## 3. Раздел /card-quality (`templates/card_quality.html`, `routes/card_quality.py`)

Одна очередь вместо двух списков:

- **Фильтры-чипы** по причинам (те же коды и счётчики, что на дашборде) +
  «Все». Активный фильтр читается из query (`?reason=`) — deep-link с дашборда.
- **Сортировка**: по эффекту (`quality_impact` desc, дефолт), score asc,
  WB-рейтинг asc.
- **API**: `/api/card-quality/list` получает параметры `reason`, `bucket`,
  `sort=impact`; фильтрация и сортировка server-side, пагинация сохраняется.
- **Строка очереди**: фото-превью, название/артикул, score, `→ +N` (impact),
  причины человеческим языком из breakdown («3 хар-ки из 38», «0 просмотров за
  30 дней»), чекбокс.
- **Массовые действия** над выбранными:
  - «⚡ Данные поставщика» и «📸 Дополнить фото» — существующие детерминированные
    bulk-флоу; страницы bulk-confirm принимают предвыбранные `product_ids`
    (сейчас сами выбирают топ-30 слабых по старым порогам — переводим на выбор
    пользователя, при пустом выборе прежнее поведение: топ-30 по impact).
  - «🤖 Исправить с ИИ» — handoff в чат (блок 4).
- **Slideover детали** остаётся: разбор по измерениям (+ причины), тренд,
  история. Кнопки «⚡ Улучшить карточку» и «🤖 Глубокий AI-анализ» заменяются на
  те же действия, что в очереди (детерминированный фикс / handoff одной карточки).

## 4. ИИ-handoff

Передача — только фронтенд через существующие endpoints чата; harness и
endpoints чата не меняются (параллельная разработка помощника не
затрагивается). Расширение агентного рантайма — аддитивное (блок 5):

1. `POST /agents/api/conversations` → `conversation_id`.
2. `POST /agents/api/conversations/<id>/messages` с телом:
   `message` — автотекст «Улучши карточки: <артикулы>. Проблемы: <агрегированные
   причины>», `product_ids` — выбранные ID `Product`, `entity_kind='product'`,
   `page_context` — fingerprint страницы card-quality (инвариант: entity_kind
   передаётся вместе с IDs, числовые ID без типа не передаются).
3. Redirect на `/agents` с открытым диалогом.

Дальше стандартный путь harness: план → подтверждение write-плана → proposals.
Лимит выбора для handoff: 50 карточек за раз (UI-ограничение, чтобы план был
обозримым).

Из `routes/card_quality.py` удаляются создание задач legacy-агентам
(`ai-analyze`, agent-часть `improve`) и импорт `agent_service`;
детерминированная часть `improve`/`proposal` (supplier diff, стандартные фото)
сохраняется.

## 5. Quality-данные в агентном рантайме

Единый помощник (и его внутренние skills) должен читать данные качества и
работать с ними после handoff:

- **Internal API** (read-only, agent-auth + assignment-to-seller):
  `POST /sellers/<id>/products/quality-brief` в `routes/internal_api.py` —
  по `product_ids` (до 50) или топ проблемных по `quality_impact` с фильтром
  `?reason=<код>`. Возвращает score, причины, impact, метрики воронки и топ-3
  рекомендации из сохранённого breakdown. Protected fields не возвращаются.
- **Platform client**: `get_card_quality_brief(seller_id, product_ids, reason, limit)`.
- **Tool** `get_card_quality` в реестре platform tools (`agents/tools.py`) —
  read-only, до 50 карточек; ReAct-skills получают его только через allowlist.
- **Skill `quality-audit`** в `agents/unified.py`: детерминированный (без LLM),
  агрегирует причины по выборке, возвращает приоритетные карточки как
  collection (`selected_product_ids` + `entity_kind='product'`) для следующего
  шага плана (например, content-writer). Регистрируется в `SKILL_CLASSES`
  и каталоге semantic planner.

## Миграция и rollout

- Новый идемпотентный скрипт `migrations/migrate_add_card_quality_v2.py`:
  колонки `Product` (6 воронки + `attention_reasons` + `quality_impact`),
  таблица `wb_subject_charcs_cache`. Проверка существования колонок/таблиц,
  повторный запуск безопасен.
- Подключение к `docker-entrypoint.sh` и `migrations/run_all_migrations.py`.
- Backfill скоров не нужен: первый `sync_card_ratings_for_seller` после деплоя
  пересчитает все активные карточки (воронка + скорер v2 + причины + impact).
  До первого синка UI честно показывает старые скоры и пустые причины.
- `AGENTS.md` обновляется в том же изменении (алгоритм, причины, handoff,
  удаление legacy-вызовов из card-quality).

## Тесты

- Скорер v2 (чистые функции): каждое измерение, fallback без конфига категории,
  дубликаты описаний, причины (все 9 кодов, границы порогов), impact.
- Парсер воронки: полный ответ, частичный (нет statistics), пустой.
- `compute_quality_summary`: reason_counts, trend, тенант-скоуп.
- `/api/card-quality/list`: фильтр `reason`/`bucket`, сортировка `impact`,
  тенант-скоуп (чужие карточки не видны).
- Bulk-флоу с предвыбранными `product_ids`: чужой `product_id` игнорируется.
- Handoff: фронтенд-логика покрывается проверкой контракта (сообщение содержит
  entity_kind + product_ids) на уровне существующих тестов harness — новые
  backend-тесты не требуются, т.к. backend чата не меняется.
- Internal quality-brief: agent-auth обязателен, tenant denial, лимит 50 ids,
  неизвестный reason → 400, protected fields отсутствуют в ответе.
- Skill `quality-audit`: агрегация причин, пустая выборка, collection-контракт
  (`selected_product_ids` + `entity_kind`), детерминированный `_usage`.

## Инварианты (не ослабляются)

- Tenant scope: все запросы `id + seller_id`; очередь и bulk — только свои карточки.
- Цены/остатки не затрагиваются: скорер читает цену, но фиксы работают только с
  контент-полями через существующий `ALLOWED_FIELDS` (`card_improver`).
- Write-действия ИИ идут только через план/подтверждение harness и proposals.
- Никаких реальных WB/LLM вызовов в unit-тестах.
