# Decisions при подготовке товаров

Продавец запускает обычную подготовку карточек. Существующие правила сначала используют точные сопоставления, ручные значения и сведения о связанном листинге. Удаление несовместимых значений, проверка количества, единиц и версии схемы выполняются локально. Решение модели допустимо только для оставшегося точного выбора по известным данным о товаре. Обычный предпросмотр показывает результат подготовки. Применение в маркетплейс выполняется через существующее подтверждение публикации.

## Контракт выбора

Категория и характеристики образуют отдельные стадии. Для категории фиксируются маркетплейс, версия дерева и допустимые пары категории и типа. Семантическое сопоставление получает короткий список типов внутри одной точно определённой категории. Для характеристики уже известны конкретный тип, версия и хеш схемы, ID атрибута, версия его словаря и доступные значения. Поля продавца и подтверждённого листинга имеют приоритет. При недостатке сведений, неоднозначном соответствии, слишком широком наборе вариантов или обязательной проверке подготовка использует прежний путь проверки.

Первый сценарий Ozon охватывает выбор типа в новой локальной карточке и поле «Цвет товара» по одному подтверждённому цвету поставщика. Кандидаты категории берутся из одного актуального узла Ozon и ограничены восемью типами. Цвет сопоставляется в текущем словаре этого типа. Точное совпадение или однозначный нормализованный цвет определяются локально. Применение выбора модели требует уверенности от 0,95 и повторной сверки исходных данных и версии. В карточках предпросмотра цвет показан рядом с другими данными конкретного товара.

Если поставщик явно соединяет цвета в одной строке, каноническая подстановка требует распознать каждую часть. Например, из `бордовый с чёрным` нельзя перенести только чёрный. Одно слово `бордо` можно сопоставить с точным словарным `Бордовый`, если значение доступно для текущего типа. Слова про светлоту и темноту не образуют список для Decisions без лексической связи с самим оттенком.

Подготовка может дополнить локальный снимок из каталога поставщика, если совпадают поставщик, источник, внешний ID и подтверждённая версия товара. Для пустой копии чтение текущего снимка подчиняется тем же условиям. Сохранённые данные продавца остаются источником для черновика. Обновление копии с неизвестной или более ранней версией идёт через действующий предпросмотр обновления от поставщика.

Фоновая проверка цвета читает настроенный CSV у активного поставщика, связанного с продавцом с подключённым Ozon. Она проверяет артикулы в файле и извлекает только явно заданные колонки цвета. Подтверждение сохраняется отдельно от каталога, если цвет из CSV буквально совпадает с цветом в снимке поставщика. Подготовка черновика использует подтверждение из локального журнала до 36 часов. Она заново сверяет поставщика, настройки источника, внешний ID, версию и цвет в сохранённой копии продавца. Приоритет имеет цвет с маркером штатного разбора каталога.

Задача запускается раз в 30 минут и читает максимум один подходящий файл за проход. Перед запросом записывается попытка с интервалом 24 часа на поставщика. Перезапуск сохраняет этот интервал. Успешный разбор заменяет подтверждения только для этого поставщика. Если подтверждённый ранее цвет разошёлся с новым файлом, новая проверка его не включает. Ошибка чтения оставляет предыдущую проверку доступной до истечения её срока.

Когда у поставщика есть артикул, подбор типа допускает его отсутствие в локальной копии при значении `NULL`. Требуются точная действующая связь, одинаковый непустой внешний ID, совпадение версии и подтверждённых названия и категории, а также непустой артикул поставщика, совпадающий с его исходным снимком. Подготовка повторно сверяет эти данные перед применением ответа. Артикул участвует в локальной проверке происхождения. Вопрос и кэш вопроса используют подтверждённые название, категорию и допустимые варианты. При расхождении заполненного артикула карточка переходит к обычной проверке.

Подготовка продолжает выбор типа в фоне после подтверждённой паузы, временной занятости кэша или нехватки времени в текущем проходе. Очередь хранит версию и подтверждение создания именно этого черновика. Продолжение допустимо только для той же версии и той же задачи. Предварительно сохранённый или изменённый продавцом черновик использует обычную проверку. Очередь планирует до трёх продолжений в пределах шести часов от запуска задачи и соблюдает нижнюю границу `Retry-After`. Неопределённый ответ, воздержание и исчерпанный дневной бюджет следуют прежнему пути проверки. Когда требуется загрузка схемы Ozon, очередь сама возвращается к выбору цвета для своего неизменённого черновика.

Запрос получает минимальные наблюдённые поля, список вариантов и возможность воздержаться. Вопрос связан с отдельным товаром через непрозрачный идентификатор в запросе. Выбранный ответ разбирается как значение из текущего точного списка. Подтверждаются актуальность источника, доступность вывода словаря и версия локального черновика. Вес, габариты, НДС, ТН ВЭД, маркировка и прочие нормативные сведения требуют собственного подтверждённого источника.

## Транспорт и бюджет

Используется OpenAI Decisions с моделью `gpt-6-luna`. Транспорт пользуется действующим серверным `AI_PROXY`, проверяет TLS и блокирует перенаправления. Физический запрос начинается после записи резервирования. Лимит задаётся на число попыток по UTC, включая неоднозначно завершённые запросы. Клиент объединяет до 32 вопросов для окна до 12 товаров.

Кэш хранит результат отдельного вопроса. Ключ включает наблюдённые исходные поля, точные варианты и версии справочников, область товара, модель и версию инструкции. При повторной подготовке того же набора кэш обслуживает уже решённые вопросы без запроса. Изменение версии схемы обновляет живые кандидаты для затронутого вопроса. Ответы кэша сверяются с текущим набором при каждом чтении. Одновременные физические вызовы ограничивает файловая блокировка поверх резервирования в SQLite. По запросу с неизвестным исходом тот же вопрос автоматически не повторяется. При HTTP 429 с подтверждённым `Retry-After` очередь соблюдает паузу провайдера. При HTTP 429 без пригодного срока действует общая пауза пять минут. При HTTP 401 и 403 пауза составляет час.

Запуск требует `OPENAI_DECISIONS_ENABLED=1`, отдельного `OPENAI_DECISIONS_API_KEY` и действительного `AI_PROXY`. Значение `OPENAI_DECISIONS_MAX_CALLS_PER_DAY` по умолчанию 100, поддерживаемый диапазон 1–1000. Кэш и резервирования размещаются в приватном файле `/app/data/openai_decisions/decisions.sqlite3` существующего тома. Для подготовки без включённого Decisions остаются локальные правила. Настройки и лимиты OpenAI Chat и DeepSeek Flash независимы.

## Проверка API на тестовых данных

Через прокси Seller Hub выполнен один запрос на семь синтетических товаров и четырнадцать вопросов. Совпали 12 ответов, включая все семь характеристик. Две широкие подборки типов закончились воздержанием. В одном запросе только для этих товаров сокращение вариантов до предметной области и добавление исходной категории дали два правильных ответа. API сообщил 3325 и 423 входных токена соответственно. Проверка показывает, как сужение вариантов помогает на этой выборке.

Собранный пайплайн проверен через тот же прокси на пяти отдельных синтетических товарах. Он сделал один запрос, получил HTTP 200 и 1995 входных токенов. Совпали четыре словарных выбора, включая чёрный и розовый чехлы. Материал пятой карточки остался без выбора. Оценки уверенности четырёх ответов составили 0,81–0,84. Повтор в обратном порядке после открытия того же файла кэша использовал ноль запросов.
