25.09.2026. Подготовка W9; это не реализованный write-контракт и не разрешение отправлять изменения.

[Основная документация](https://docs.ozon.ru/api/seller/) при текущем обращении через web-fetch не открылась. Официальные `/api/seller/swagger.json` и `/api/seller/en/` также вернули redirect loop; схема из этих адресов не получена. Неофициальные GitHub/Postman зеркала обнаружены поиском, но не приняты как подтверждение request/response contracts. Новые методы не добавлены в runtime allowlist; реальных shipping/reply calls не выполнялось.

После получения актуального официального контракта:

1. Зафиксировать supported schemes и полную матрицу statuses/actions; FBS/rFBS не объединять по сходству названий.
2. Добавить exact read preflight с ограниченным бюджетом, отдельный durable proposal и human confirmation. Просмотренный состав/упаковки/версия должны совпасть перед единственной физической записью.
3. Потерянный ответ и 200 без конечного результата ведут в reconciliation, без слепого повторного ship/reply.
4. Для маркировки и документов использовать только факты продавца и официальные требования; отсутствие кода не восполнять догадкой.
5. Файл этикетки: scoped ownership, bounded size/content type, защищённая выдача и понятный статус подготовки. Проверить PDF и принадлежность конкретным отправлениям.
6. UI: состав → требования → проверяемый preview действия → явное подтверждение → наблюдённый результат. Список/поиск/Back не теряют контекст, двойная отправка блокируется до сверки.
7. Synthetic contract/E2E сначала; затем один representative реальный заказ/ответ после конкретного review. Read-only обзор заказа не закрывает этот gate.
