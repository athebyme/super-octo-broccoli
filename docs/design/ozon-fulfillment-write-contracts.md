Сверка 20.11.2026. При объявлении методов отзывов и вопросов Ozon указал Premium Plus. Обновление 07.10.2025 перечисляет методы отзывов v1, включая создание комментария, среди доступных с Premium Plus и Premium Pro. Для актуальной версии каждого метода требуется подтверждение тарифа и фактического доступа кабинета. Причина наблюдавшегося `403` остаётся неизвестной. [Первоначальное объявление Ozon](https://dev.ozon.ru/news/495-Metody-otzyvov-voprosov-otvetov-poiavilis-v-Seller-API) · [Обновление Premium Pro](https://dev.ozon.ru/news/634-Novye-metody-dlia-poiskovykh-zaprosov-v-Seller-API/)

С 17.11.2026 для FBS доступен отдельный сценарий пломбирования экземпляров. Ozon документирует признак `sealing_allowed` и разрешённые действия `set_seal_number` и `edit_seal_number`. Сценарий привязан к экземпляру товара и включает установку номера, проверку статуса и завершение сборки. При реализации отгрузки нужно учитывать текущие возможности конкретного отправления и сверку статуса каждого экземпляра. [Сценарий пломбирования Ozon](https://dev.ozon.ru/news/842-V-Seller-API-poiavilas-podderzhka-plombirovaniia-tovarov-FBS/)

Модератор Ozon уточнил, что на запрос до 20 отправлений возвращается один `task_id` для общего PDF. Запрос с одним отправлением связывает задание с ним однозначно. Для общей выдачи указаны порядок отправлений либо данные отправления на самой этикетке. Обработка нескольких страниц требует сверки номера или штрихкода на этикетке. Точные форматы статусов задания, полей ответа и файла ещё требуют подтверждения. [Разъяснение Ozon](https://dev.ozon.ru/community/2371-Metod-dlia-sozdaniia-zadanii-na-formirovanie-etiketok/)

В Seller Hub остаются просмотр FBS, локальные черновики ответов и переход в кабинет продавца. Ноябрьская сверка была по публичным источникам. Seller API аккаунта не вызывали.

[Основная документация](https://docs.ozon.ru/api/seller/) при текущем обращении через web-fetch не открылась. Официальные `/api/seller/swagger.json` и `/api/seller/en/` также вернули redirect loop; схема из этих адресов не получена. Неофициальные GitHub/Postman зеркала обнаружены поиском, но не приняты как подтверждение request/response contracts. Новые методы не добавлены в runtime allowlist; реальных shipping/reply calls не выполнялось.

После получения актуального официального контракта:

1. Зафиксировать supported schemes и полную матрицу statuses/actions; FBS/rFBS не объединять по сходству названий.
2. Добавить exact read preflight с ограниченным бюджетом, отдельный durable proposal и human confirmation. Просмотренный состав/упаковки/версия должны совпасть перед единственной физической записью.
3. Потерянный ответ и 200 без конечного результата ведут в reconciliation, без слепого повторного ship/reply.
4. Для маркировки и документов использовать только факты продавца и официальные требования; отсутствие кода не восполнять догадкой.
5. Файл этикетки: scoped ownership, bounded size/content type, защищённая выдача и понятный статус подготовки. Проверить PDF и принадлежность конкретным отправлениям.
6. UI: состав → требования → проверяемый preview действия → явное подтверждение → наблюдённый результат. Список/поиск/Back не теряют контекст, двойная отправка блокируется до сверки.
7. Synthetic contract/E2E сначала; затем один representative реальный заказ/ответ после конкретного review. Read-only обзор заказа не закрывает этот gate.
