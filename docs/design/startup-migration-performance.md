# Проверяемое сокращение времени миграций

Контекст W8 Ozon: 25.09 обновление аналитики потребовало повторного полного Docker migration bundle. После старта контейнера в 11:23:15 UTC приложение дошло до healthy перед браузерной приёмкой около 11:31 UTC. Схема этого выпуска не менялась. Предыдущий guard намеренно включает весь backend Python, потому что migration path импортирует приложение и runtime helpers; его dependency scope не сокращается без доказанного closure.

## План

1. На изолированной восстановленной базе измерить существующие команды, сохранив полный entrypoint и действующий success journal. Профиль содержит только имя script, длительность и exit code, без аргументов/credentials/SQL/строк БД.
2. Проверить гипотезу: стоимость составляют повторные полные `foreign_key_check` между неизменяющими миграциями. Если она подтверждается, объединить подходящие последовательные `apply_migration(connection)` в один connection с commit после каждого шага. Rebuilds и специальные миграции сохраняют самостоятельные пути и порядок.
3. Разрешить повторное использование только реально выполненного полного FK scan внутри явного ограниченного scope того же connection. `total_changes`, transaction state, `main.schema_version` и `main.data_version` должны совпасть. Новая DML/DDL, внешний writer, другое соединение, выход из scope или неустойчивый scan запрещают cache hit. Managed legacy orphan проверяется заново против набора таблиц каждой миграции даже при reuse.
4. Проверить fresh/historical/repeat/interrupted migrations, rollback текущего шага, отсутствие запуска следующего при ошибке, актуальность snapshot при локальной/внешней записи. Сравнить схему, violations и защищённые данные на реальной копии; повторный startup обязан использовать обычный guard.
5. Только после измеримого ускорения и полной проверки подготовить exact image, пройти production startup и read-only приёмку. Bundle digest, исключение одновременных writers, fail-fast и запись success только после всего bundle остаются обязательными.

Результат не является переносом SQLite в multi-host, live migration поверх работающих writers или обещанием нулевого downtime. Старые архивы и rollback image сохраняются.

## Основания

`PRAGMA data_version` имеет смысл сравнивать во времени на одном connection; commit этого же connection его не меняет. Поэтому для локальных изменений дополнительно нужен `total_changes`, а для DDL — наблюдённая версия схемы. [SQLite PRAGMA](https://www.sqlite.org/pragma.html#pragma_data_version), [SQLite total_changes](https://www.sqlite.org/c3ref/total_changes.html). Кэш не переносится между connections или процессами и не подменяет первоначальную проверку.

## Измеренный baseline и реализация

Старый image `6282ec860fc2…` на восстановленной копии завершил штатный guard за **430,993 секунды**. Начальный блок — 149,574 секунды; отдельные повторные FK-проверки — около 16 секунд. Прототип подтверждает reuse: после первой 16-секундной проверки следующие неизменённые media migrations выполняются примерно за 0,002 секунды.

Runner принимает только заранее проверенные migration paths и сохраняет полный исходный порядок. Shared шаги вызывают существующий `apply_migration` с исходным foreign_keys mode; special/rebuild шаги выполняются существующей отдельной Python-командой, со своим соединением и транзакциями. Общее соединение в это время не держит транзакцию. После записи дочерней команды его data_version требует нового scan; если данных не меняли, доказательство сохраняется. Дальнейшие шаги после любой ошибки не выполняются.

**114 tests + 5 subtests passed**, включая все migration tests, свежие и повторные реальные groups, сохранение исторических строк, неустранимые managed orphans, schema/local/external mutation, изменение connection factories, isolated standalone commands, rollback/stop и release cache на исключении.

Финальный candidate завершил полный guard на восстановленной базе за **314,460 секунды** вместо **430,993**: сокращение на **27,04%**. Это последовательные измерения на одном сервере, а не статистический benchmark. Схема (777 объектов), все FK observations (21 прежнее legacy-нарушение вне затронутых доменов) и полные хеши пяти защищённых таблиц совпали. Ни исправление прежних orphan rows, ни отсутствие нарушений во всей исторической базе этим не утверждается.

На пустых базах штатный guard старого и нового образов завершился за 27,280 и 24,735 секунды; схемы совпали, `quick_check=ok`, FK violations отсутствуют. Повторный штатный guard обоих образов использовал собственный success journal. Полное приложение на восстановленном снимке прошло 5 браузерных сценариев / 36 layouts, 1 898 SKU на 19 API-страницах, с точной сверкой данных и без provider calls.

Production image `0632b1e7e6cf…` запущен 25.09 в 18:56:55 UTC; приёмка завершена в 19:04:36 UTC, healthy, 0 restarts. На production полный migration bundle занял 338.437 секунды. [Результат выпуска и ограничения](../operations/2026-09-25-startup-migration-performance.md).
