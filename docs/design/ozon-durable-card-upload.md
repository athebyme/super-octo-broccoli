# Ozon card upload v3 — frozen implementation contract (2026-09-27)

Scope: local card preparation followed by a separate, explicit, version-reviewed publication. No provider calls, media fetching, price/stock writes, or product write operations occur in the preparation HTTP request or preparation worker. `MarketplaceOperation` remains the sole owner of a physical Ozon write, task polling, uncertainty, quarantine, and provider readback. The current `source_sync` behavior is not available for new runs.

## Two run modes and consent

- `source_prepare`: seller selects 1–200 exact owned `ImportedProduct.id` values and an active owned Ozon account. Acceptance and worker require `MARKETPLACE_OZON_ENABLED`; they do **not** require `MARKETPLACE_OZON_PUBLICATION_ENABLED`, connected credentials, or an unexpired key. The worker may perform only local source-link reconciliation, observed-mapping reconciliation, missing observed-fact hydration, create/rebase/apply local defaults, and validation. A ready draft becomes `prepared`, never a queued `MarketplaceOperation`. Missing seller facts become `needs_input`; stale official reference becomes `waiting_reference`. Preparation completion means drafts are ready for review, not uploaded.
- `reviewed_drafts`: seller selects 1–200 exact owned drafts of one account and submits an exact `{str(draft_id): integer_version}` map plus explicit `confirm_write=true`. Acceptance requires both Ozon and publication flags, active/connected account and current credentials. It captures immutable ordered draft IDs, imported product IDs, versions, and optional parent preparation run. Worker rechecks exact seller/account/draft/version, fresh schema, publishable state, listing identity, and quarantine before atomic enqueue. It never hydrates, rebases, chooses type, or fills defaults after review. Drift yields typed `needs_input` and no operation. If a flag is disabled after acceptance, the worker waits without creating new operations; already-attempted operations continue read-only reconciliation under existing rules.
- The modes are never implicitly converted. `/from-drafts` without a complete version map fails with `draft_review_required`; classic must post reviewed versions. Retry of a `reviewed_drafts` run requires a fresh review and new exact versions; it cannot invoke source preparation or replay uncertain operations. Source preparation retry is local-only and requires a new explicit request key. Existing legacy source-sync operations remain readable but are never re-authorized by v3.

## Minimum schema (schema agent owns models and migration)

`OzonBulkUploadRun` (`ozon_bulk_upload_runs`): `id INTEGER PK`; `job_id INTEGER NOT NULL UNIQUE` FK `background_jobs.id` with NO ACTION/RESTRICT; `seller_id INTEGER NOT NULL` and `account_id INTEGER NOT NULL` scoped account identity; `mode VARCHAR(24) NOT NULL CHECK IN ('source_prepare','reviewed_drafts')`; `request_key_hash CHAR(64) NOT NULL`; `request_fingerprint CHAR(64) NOT NULL`; `created_by_user_id INTEGER NULL`; `parent_prepare_run_id INTEGER NULL` self-FK with NO ACTION/RESTRICT; `state VARCHAR(12) NOT NULL DEFAULT 'active' CHECK IN ('active','completed')`; `next_due_at DATETIME NULL` (non-NULL for active, NULL for completed); `last_attempt_at DATETIME NULL`; `lease_token CHAR(32) NULL`; `lease_until DATETIME NULL`; `created_at` and `updated_at` UTC DATETIME NOT NULL. Constraints: `UNIQUE(seller_id,request_key_hash)`, `CHECK ((lease_token IS NULL) = (lease_until IS NULL))`, `CHECK ((state='active') = (next_due_at IS NOT NULL))`. Indexes: `(state,next_due_at,last_attempt_at,id)` for due selection and `(seller_id,account_id,created_at,id)` for history. An optional parent is an owned `source_prepare` run of the same account; selected drafts must match its exact imported-product identities. The parent link is navigation/provenance, not publication authorization: a seller may fix a `needs_input` draft or publish prepared items while the rest still wait, provided each chosen current draft version is explicitly reviewed. Request key is 24–128 URL-safe random characters (UI uses a generated UUID or stronger token), stored only as a SHA-256 hash scoped to seller. Canonical fingerprint covers mode, account, ordered exact IDs, reviewed versions, and parent ID. Same key/fingerprint returns the existing job; same key with different input returns 409. SQL uniqueness decides races.

`OzonBulkUploadItem` (`ozon_bulk_upload_items`): `id INTEGER PK`; `run_id INTEGER NOT NULL` FK run with NO ACTION/RESTRICT; `ordinal INTEGER NOT NULL CHECK ordinal>0`; `imported_product_id INTEGER NOT NULL` immutable logical identity snapshot; `reviewed_draft_id INTEGER NULL`, `reviewed_version INTEGER NULL`; `draft_id INTEGER NULL`, `prepared_version INTEGER NULL`; `operation_id INTEGER NULL` FK `marketplace_operations.id` with NO ACTION/RESTRICT, immutable once set; `phase VARCHAR(40) NOT NULL CHECK IN ('pending','preparing','waiting_reference','needs_input','prepared','reviewed','operation_linked','needs_manual_reconciliation','failed_local','excluded')`; `next_due_at DATETIME NULL`; `reference_wait_started_at DATETIME NULL`; `local_failure_count INTEGER NOT NULL DEFAULT 0 CHECK (local_failure_count BETWEEN 0 AND 3)`; `title_snapshot VARCHAR(300) NOT NULL`; `offer_id_snapshot VARCHAR(200) NULL`; `error_code VARCHAR(100) NULL`; `error_message VARCHAR(700) NULL`; `created_at` and `updated_at` UTC DATETIME NOT NULL. Source items start `pending`; reviewed items start `reviewed`. Constraints: `UNIQUE(run_id,ordinal)`, `UNIQUE(run_id,imported_product_id)`, both reviewed fields NULL or both valid positive; `phase='operation_linked'` implies `operation_id IS NOT NULL` (legacy `excluded`/manual-review items may retain a known operation ID); `phase='prepared'` implies non-NULL draft ID/prepared version; `phase='reviewed'` implies non-NULL reviewed draft/version. Indexes: `(run_id,phase,next_due_at,ordinal)` and `(operation_id)`. Imported product and draft IDs are logical snapshots, not cascading FKs: every worker step rechecks exact live seller/account scope, while history survives source deletion. No audit row is silently cascade-deleted; schema agent verifies account/seller deletion and existing BackgroundJob cleanup behavior in migration tests.

`BackgroundJob(job_type='ozon_bulk_upload')` remains the public UID and bounded summary. V3 `progress_data` is a small versioned pointer/summary, not a second source of truth for item→operation links; `public_document` joins run/items/operations and keeps the existing `job_uid`, account, summary, items shape with an added explicit `mode`. `status=completed` for `source_prepare` means local preparation finished, and its summary reports `prepared` separately. For `reviewed_drafts`, `succeeded` means Ozon import task confirmation (or proven update/no-op), not moderated, for sale, or catalog-observed. These facts need separate freshness in the listing view.

## Service and route contracts

- `OzonBulkUploadService.accept_source_prepare(seller_id,account_id,imported_product_ids,request_key,created_by_user_id)` and `.accept_reviewed_publish(seller_id,account_id,draft_ids,expected_versions,request_key,parent_prepare_job_uid=None,created_by_user_id=None)` do only bounded ownership/version prechecks and one atomic BackgroundJob+run+item insert; return the persisted job immediately. No expensive source-link scan or per-item draft preparation in POST.
- `.find_by_request_key(seller_id,request_key)` is read-only and returns the same seller-scoped job or 404. `.run_due_preparation(now=None,run_limit=20,item_limit=40,seconds_budget=45)` selects due active runs by `(next_due_at,last_attempt_at,id)` with an expiring 120-second CAS lease, one round-robin item per run before taking more, maximum 20 items per run/tick. Result is `{selected,processed_items,prepared,enqueued,waiting,needs_input,busy,failed}`. One existing scheduler thread invokes it; no new scheduler thread. Local draft methods may commit their own small transactions, but no SQL write transaction spans provider or media I/O. The worker commits draft identity/version to its item before publication enqueue. Retry of transient local failure is bounded to 3 attempts with durable due; unknown commit outcome is re-read by exact item identity before any action.
- `MarketplacePublicationService.enqueue_reviewed_upload_item(...)` repeats payload/schema/quarantine checks and creates `MarketplaceOperation` + snapshot + sets the exact item `operation_id` + updates public summary in **one DB transaction**. Refactor `_create_operation` to support a no-commit internal path; other existing callers keep their current commit behavior. If an equivalent active operation already exists, link only after exact seller/account/draft/kind/request-fingerprint proof; never recover by a loose draft-only search when a v3 item exists. Queued operation submission still passes the existing account lock, quarantine, live preflight, quota, single-attempt transport, and readback gates.
- `.reconcile_active_runs` mirrors only exact linked operation IDs, rotates due jobs even on no-change reference waits, and never submits a write. A GET may derive fresh state but does not run source preparation or provider calls. Reference wait retains the existing 6-hour cap and a future due; first 20 waiting jobs cannot starve job 21.
- Canonical `POST /marketplaces/ozon/uploads/` accepts strict `confirm_prepare=true`, `request_key`, account and product IDs for local preparation. The old `confirm_write` source-sync body fails closed with a typed `review_required` response; it is not silently reinterpreted. `POST /from-drafts` accepts strict reviewed versions, `confirm_write=true`, `request_key`, optional parent UID. Both return 202 `{success:true,run:{job_uid,mode,status,account_id,summary,...},replayed:false|true}` plus `Location: /marketplaces/ozon/uploads/<job_uid>`. A duplicate returns the same UID and `replayed:true` regardless of current completion. `GET /api/by-request` reads `X-Upload-Request-Key` header and returns the same scoped run document without a POST/provider call, or 404 if no committed run; a 404 after a lost response never triggers an automatic new POST. Detail/list remain seller-scoped. The reviewed retry endpoint returns 409 `draft_review_required` with a safe link to fresh draft review. Classic forms include hidden request key and exact reviewed version inputs.

## Legacy, retention, and acceptance

Migration is idempotent and does not rewrite existing physical operations. For legacy v1/v2 run items with an explicit operation ID, verify seller/account/draft/offer identity before binding; then only mirror the existing operation. Missing operation ID may bind only one provably exact operation; ambiguity or a preparing item without draft identity becomes `needs_manual_reconciliation`, never `failed/safe_retry`. Legacy waiting-reference without an operation can continue local-only preparation, but never auto-enqueue a new write under the old source-sync consent. No automatic replay of attempted/uncertain operations. `BackgroundJob` has no observed automatic cleanup path; the new restrictive FKs mean future cleanup must explicitly retain/export audit or delete child rows in a reviewed retention migration. Do not add an implicit cascade or run-history purge in this package.

Inherited limits: 200 items/run, 512 KiB public progress ceiling, 50 per publication chunk where other callers still use bulk enqueue, 6-hour reference wait, 24-hour publication operation deadline, one physical write attempt. New preparation worker hard caps: 20 runs selected, 40 local item steps and 45 seconds per tick, at most 20 items from one run, 120-second lease, at most 3 local failure retries. These are safety ceilings, not a throughput promise; measure 200 real local drafts, DB writer time and RSS before tuning. Provider scheduler fairness for 20 long-pending tasks versus queued item 21, quota-read 429 Retry-After defer, create task versus catalog-observed readback, source freshness, and provider/category contract are explicit follow-up packages, not silently claimed complete by this durable core.

Required tests: same-key lost POST/different fingerprint/parallel insert; seller/account/CSRF and source preparation while publication flag off; source mode produces 0 MarketplaceOperations/provider calls; reviewed exact versions and schema drift produce no operation; kill after local draft commit, before/after atomic operation+item commit; 21+ waiting jobs plus ready job fairness; restart/lease expiry; legacy explicit/ambiguous links with no replay; 200-item real local preparation budget and bounded progress; operation status/readback with one physical attempt and no automatic uncertainty replay. Offline provider spies and browser readback; no live provider write is authorized by this contract.

## Approved delta 1 (2026-09-27)

The parent approved a nullable `UNIQUE(operation_id)` constraint on v3 items: one physical operation belongs to at most one new run item. A different request key encountering an active exact operation receives typed `already_in_progress` with an owner-scoped operation review link; it does not appropriate that operation or issue another write. Historical legacy journals may still display the same already-existing operation read-only, without creating duplicate new item links or treating it as a safe retry. `OzonBulkUploadRun.seller_id` and `.account_id` use NO ACTION/RESTRICT FKs, with migration tests for attempted account/seller deletion; audit rows do not disappear by cascade. `find_by_request_key` requires `seller_id`, `account_id`, and request key, and performs account-scoped lookup. This delta supersedes only schema uniqueness/FK/lookup wording above; all other contract terms remain unchanged.

## Approved delta 2 (2026-09-27)

Both new accept methods return immutable `UploadRunAcceptance(job: BackgroundJob, replayed: bool)` rather than a bare job. `replayed` is determined after the unique request-key insert or its IntegrityError race recovery, not by a prelookup alone. The JSON 202/Location response uses that exact flag; classic redirects to `acceptance.job`. The ordered exact ID array remains part of the request fingerprint. `public_document(detail=True)` remains bounded to 200 items and retains existing optional item/summary fields while adding the explicit mode/phase distinction.

## Approved delta 3 (2026-09-27)

`OzonBulkUploadRun.mapping_preflight_at DATETIME NULL` is an additional no-default marker. It is set only after the existing full seller-scoped observed category-mapping scan reports `success=true`, with the current run lease token and expiry rechecked in the marker transaction. The scan is a separate bounded worker step, never in HTTP and never repeated for each selected item. A busy mapping lock defers the run; a truncated or otherwise incomplete full scan does not bless the selected subset and requires manual category review. The scan must not start after the worker tick budget is exhausted. This delta does not change the immutable request fingerprint or authorize a provider write.

## Additional root-approved implementation boundaries

The schema migration creates empty additive tables; legacy adoption is bounded runtime work, not a startup JSON rewrite. Recheck both lease token and expiry on every transition and within the atomic operation/item commit. JSON creation returns 202 plus Location; classic forms redirect 303 to the same persisted job.


Root scheduling delta (2026-09-27): the existing singleton APScheduler registers a separate `prepare_ozon_uploads` job every10s, max_instances=1/coalesce, invoking run_limit20/item_limit40/seconds_budget8. No custom thread/executor is introduced. The minute provider-operation poll remains independent. Service default45s is a maximum callable ceiling, not the runtime scheduler budget.
