# Ozon: разбор неизвестного результата и остановка новых изменений

26.09.2026, 20:14 МСК. **Развёрнуто и принято:** production `595fa6cb7ea7…`, healthy/0 restarts. 1634 tests +452 subtests, exact-image 52 browser scenarios/272 layouts, actual backup/migration rehearsal и read-only production 240 layouts/73 фото. Реальные quarantine decisions ради проверки не создавались. [Отчёт с доказательствами и ограничениями](../operations/2026-09-26-ozon-operation-quarantine.md). Внешние backups отложены владельцем. Ниже legacy stop-only действие явно отделено от нового общего ограничения.

## Проверенные исходные факты

В исходном production `29a5f754e159…` метод `MarketplacePublicationService.resolve_uncertain` останавливает автоматическую сверку, освобождает только локальную квоту и оставляет `status=uncertain`, attempt_count и snapshots. Это прежняя кнопка «остановить проверку», а не карантин товара: решение хранится в mutable request summary, отдельной истории решений и общего запрета новых записей по товару нет. Partial unique index защищает текущий draft, а не все публикации/цены/остатки того же provider identity. Commercial имеет отдельный scheduler/readback и не принимает publication manual-stop. Media model/workflow отдельный; **standalone Ozon media сейчас prepare-only**, write path подключён к WB. Нельзя объявить Ozon media отправку работающей либо затронуть WB в этом пакете. Фото Ozon уже входят в full-state product import/update.

Реальные uncertain publication #6 и price #7 остаются историей; price #8 succeeded отдельно вернула цену. Их статусы, попытки, расписание и ограничения ради теста не менять. Новый карантин создаётся только после явного решения пользователя в новом интерфейсе, не автоматическим backfill старых uncertain.

## Полный результат пакета

Продавец/владелец открывает неизвестный результат, видит факты отдельно от решения, сохраняет объяснение и явным действием останавливает **новые изменения конкретного товара в выбранном кабинете**. Новая операция с другим idempotency key, новый черновик, массовая отправка, queued scheduler и rollback не обходят ограничение. Чтение, ручная сверка уже attempted операции и ротация ключа продолжают работать. Остальные товары/кабинеты/WB не затронуты. Нельзя вручную объявить unknown успешным или неуспешным.

Карантин — операционное решение, не доказательство provider outcome. Если исход удалось подтвердить штатной сверкой, его можно отдельно снять по просмотренной версии. Пока исход остаётся неизвестным, разрешения на blind repeat нет; «снять запрет потому что прошло время» не добавляется. Для никогда не доказуемого исхода честное конечное состояние — зарегистрированное решение + постоянная видимая область запрета; другие товары продолжают работать. Отдельное разрешение после внешнего доказательства/нового подтверждённого current-state потребует собственного evidence-контракта, а не текстового checkbox обхода.

## Реализация и доказательство снятия

[`MarketplaceWriteQuarantine` и `MarketplaceWriteQuarantineEvent`](../../models.py) хранят область/состояние `active|released` по точному seller/marketplace/account и отдельные `placed`, `note_added`, `released` с автором, временем и причиной. [Additive-миграция](../../migrations/migrate_add_marketplace_write_quarantine.py) запускается после `migrate_add_marketplace_media_publications.py` в Docker batch, прямом старте приложения и comprehensive runner. Исторические uncertain операции не получают выдуманных карантинов. В [серверном определении области](../../services/ozon_quarantine_scope.py) точная цель выводится только из сохранённых operation summary и snapshots: согласованные offer_id и известный Ozon product_id дают товар, повреждённый или конфликтующий target — весь кабинет. Просмотренная версия операции и server-owned scope token проверяются снова под account lock; выбранный пользователем текст не задаёт identity.

[Сервис решений](../../services/ozon_write_quarantine.py) сохраняет решение и событие одной транзакцией, проверяет активного и не заблокированного владельца, а перед первой физической попыткой общий gate повторно проверяет исходный account и offer/product identity. Запрет охватывает карточку, цену, остатки **на всех складах** и фото внутри полного product write; queued attempt=0 завершается локально без HTTP и без увеличения попыток. Ручная read-сверка уже отправленной операции разрешена. Старое `resolve_uncertain` остаётся отдельным legacy-действием: оно останавливает polling только одной publication operation и само по себе не создаёт карантин.

Снятие разрешено после отдельного просмотра версии исходной операции и версии карантина, причины и явного подтверждения. Проверяется исход именно этой операции: для commercial — exact confirmed/submitted live state и тип цены либо склада; для failed product task — нормализованный отказ исходного item; для archive — подтверждённое архивирование exact offer/product; для успешного create/update — source, время завершения, согласованный item result, полный сохранённый confirmed state и его fingerprint. Update восстанавливает full payload из сохранённого confirmed state; допустимое расхождение с отправленным payload ограничено зафиксированным при штатной сверке `8229` (import-only «Тип») и `9024` (канонизация offer_id), с повторным сравнением всех остальных полей. Текущий черновик, справочник или поздняя операция другого товара не служат доказательством. `partial` и по-прежнему `uncertain` не дают снять запрет. Снятие не отправляет новый запрос Ozon и не меняет исходную попытку.

Экран: `/marketplaces/operations/<id>/review` ([шаблон](../../templates/ozon_operation_review.html), [Vue-код](../../static/ozon-operation-review.js), [routes](../../routes/marketplace_operations.py)). Его JSON API читает preview и страницы журнала; POST сохраняет остановку или запись/снятие, с CSRF, просмотренными версиями и явным confirmation. При потерянном ответе интерфейс сначала перечитывает решение и не повторяет POST автоматически. Предпросмотр показывает точную или широкую область до действия, а журнал отделён от статуса Ozon. Экран принят на production `595fa6cb7ea7…`; старые uncertain операции не получают решений автоматически.

## Контракт и критерии проверки перед выпуском

1. **Источники и границы записи.** Зафиксировать все physical boundaries текущего Ozon runtime: import/update, create compensation/archive, update rollback, price/stock single и batch, queued dispatch. Входные формы/enqueue получают раннее объяснение, но решающий gate повторяется под тем же account lock непосредственно до durable attempt=1. Attempts>0 идут только в прежнюю read reconciliation. Будущая standalone Ozon media не должна обойти общий gate; текущий WB write не меняется.
2. **Persisted scope и append-only решения.** Additive `MarketplaceWriteQuarantine` + `MarketplaceWriteQuarantineEvent`: exact seller/marketplace/account, originating operation либо media operation (XOR), immutable scope, active/released, optimistic version, UTC timestamps; события placed/note_added/released после доказанного исхода. Origin uniqueness не допускает повторного hold от потерянного POST. Actor — authenticated active owner, не произвольный user ID. Причина bounded plain text; никакого key/ciphertext/fingerprint/raw API body в журнале/ответе. ORM mutation + audit в одной короткой транзакции. No backfill выдуманных решений.
3. **Определение scope только на сервере.** Из immutable committed request/snapshot извлечь exact offer_id и, когда доказан, provider product_id. Current edited draft/title/source не становится identity evidence. Все доступные immutable identity fields должны согласоваться и принадлежать original account. Listing ID используется для навигации, а не как единственный write fence. При неизвестном/противоречивом target невозможно притвориться точным товаром: preview предлагает явно подтверждаемый account-wide запрет и объясняет его ширину. Client не задаёт scope/identity самостоятельно; GET preview + exact source operation version + reviewed scope fingerprint привязывают подтверждение к увиденному состоянию.
4. **Постановка и обслуживание.** Только uncertain operation, после физической попытки, под account lock с fresh owner/version. Остановка automatic reconciliation и освобождение local quota атомарны с карантином; provider status, попытки, external task, submitted/before/confirmed snapshots не перезаписываются. Note не снимает ограничения. Повторный уже принятый запрос не создаёт второе событие. Ошибка/занятый lock/чужой actor не оставляют частичного успеха. Caller-owned dirty/flushed transaction не должна теряться.
5. **Снятие.** Только отдельное явное подтверждение viewed quarantine + operation revisions, active owner и тот же lock. Исход original operation должен быть доказан штатным workflow (точный kind-aware terminal contract, не partial/uncertain и не одна ссылка на чужую succeeded operation). Решение не отправляет write и не ставит original в queued. Не выполнять release по текущему статусу другой price operation (#8 не переписывает исход #7).
6. **Серверное применение запрета.** Exact matching по account + сохранённым offer/product identity; product hold охватывает карточку/цену/остатки/полную галерею, включая warehouses, и это явно показано до подтверждения. Account fallback блокирует все новые writes кабинета. У поставленной ранее queued attempt=0 операции понятный локальный исход без HTTP/attempt increment; batch не должен частично отправить просмотренный frozen набор, если один его товар заблокирован. Already-attempted read и exact idempotent readback старого request остаются доступными. Отключение ключа не смягчает прежние attempted-write gates. Held quarantine survives restart/deploy/key rotation.
7. **Vue UX.** Новый seller-scoped экран «Разбор результата» в общей теме, с обратным переходом к операции и магазину. Вверху товар/фото при exact available identity, тип изменения, дата, честный исход и последняя сверка. Ниже отдельный блок «Остановить новые изменения»: явная область действия, последствия, причина, confirmation. После решения — что остановлено, что доступно, журнал автора/времени/причины; нет зелёного success операции от принятого local решения. Error/empty/busy/session/conflict/lost POST сохраняют ввод, readback не повторяет POST; review action не обновляет viewed revision в фоне. На operation/health/commercial/draft entry surfaces видна ссылка на точную причину запрета. Технические fingerprints остаются в audit, не в основном user flow.
8. **Проверки.** Service/API: owner/foreign/actor/type/version/lock, malformed immutable scope, offer reuse/product rename, account fallback, independent seller/account/WB, atomic rollback, duplicate/lost request, release eligibility and note concurrency. Provider spies на **каждом** physical boundary и queued/batch/rollback — вызовов/attempt increments=0 при hold; attempted read remains available. Migrations fresh/ORM/historical/repeat/interrupted/FK; strict schema validation. Real Flask/CSRF/Vue: product и account preview, reason/focus, conflict, lost POST/readback, pagination, read-only production. 320/390/768/1440, обе темы, 200% reflow, keyboard; screenshot critique до выпуска.
9. **Выпуск.** Exact current production base + bounded runtime files, full offline regression и exact-image browser, реальное восстановление local backup и additive rehearsal, unchanged protected operations/keys/drafts/proposals. В production не создавать/снимать реальный карантин без отдельного осознанного действия владельца; smoke только читает новые страницы и disabled/action eligibility. Отдельный отчёт, обновление AGENTS/runbook/readiness/user guide, редкий общий Telegram после принятия.

## Дизайн и критика

Существующая «Тёплая редакция»: Inter для рабочего интерфейса, текущие light/dark tokens, accent только для главного подтверждаемого действия, нейтральный фон неизвестного исхода и ясный текст. Иконки lock/clock/info из текущего набора, реальные exact-owned фото с placeholder. Декоративные изображения и imagegen здесь не помогают принять решение. Layout: breadcrumb → результат/товар → область остановки и форма → журнал; mobile складывает факты и кнопки вертикально. Контраст/focus/перенос длинных offer/reason проверяются. Нет декоративной dashboard-сетки и смешения «local решение принято» с «Ozon подтвердил запись».

Главные риски: gate только на кнопке либо только на исходном draft не защищает scheduler/другой proposal; mutable identity может пропустить тот же provider product после переименования; глобальный запрет без объяснения мешает всему магазину; release по свободному тексту уничтожает смысл single-attempt. Поэтому scope immutable, gate общий на физических границах, fallback явно широк, outcome и disposition отдельны. План не разрешает новые provider endpoints, повторные price-details/inbox probes или неавторизованные реальные writes.
