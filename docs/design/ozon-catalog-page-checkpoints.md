# Ozon catalog: возобновление чтения внутри страницы

**Статус 26.09: реализовано в candidate worktree; frozen focused 59 tests + 3 subtests и synthetic capacity прошли. Production-приёмка ещё не выполнена.** Ниже сохранён исходный проект; фактические caps, TTL/reclaim и доказательства уточнены в [отчёте выпуска](../operations/2026-09-26-ozon-resumable-reads-and-vue-review.md) и корневом AGENTS.md. 64/512 MiB и 30 минут приняты как локальные runtime caps по representative synthetic измерению, не как upstream quotas или универсальный worst case.

> Исторический текст проекта (статус реализации указан выше).

**Статус: проект, не реализовано и не проверено.** Это разбор риска на синтетическом ответе, который проходит текущие page contracts; свидетельства сбоя у live Ozon нет. Никаких новых Seller API endpoints, повышенных лимитов или изменения production этим документом не вводится.

## Почему существующего cursor недостаточно

`services/ozon_account_sync.py` разрешает не более 12 read calls и 45 секунд старта вызовов за tick; `services/marketplace_listings.py` сначала читает product list и product info, затем до 20 cursor-страниц **каждого** из attributes, prices и stocks. Успешный list-page с 13 страницами attributes уже не помещается в tick: после локального `ozon_read_budget` `MarketplaceCatalogSync.cursor` ещё не сдвинут, потому что `_apply_catalog_page` коммитит только полную страницу. Следующий tick перечитывает list и ранние enrichment pages. После восьми таких transient failures job останавливается, хотя ответы сами по себе могут быть допустимы. Верхняя оценка текущего чтения одной страницы — `1 list + 1 info + 20×3 = 62` вызова; 12 повышать нельзя.

Цель — разделить **чтение** страницы на durable части, сохранив один атомарный commit её listing projections, link reconciliation и `MarketplaceCatalogSync` cursor. `seen_count`, `page_count`, `last_seen_at`, phase и UI-прогресс отражают только применённые страницы. Неполная staging-страница не становится доступным каталогом и не участвует в finalizer, который помечает unseen товары unavailable.

## Предлагаемая граница страницы

Сохранять обычный `MarketplaceListingService.PAGE_SIZE=1000` и текущий `MAX_ENRICHMENT_PAGES=20`. Для 8719 товаров запрос с `limit=20` дал бы минимум 436 list pages и примерно 73 минуты при одном завершённом page/tick раз в 10 секунд, вместо примерно девяти страниц текущего размера до учёта archived phase; это недопустимый регресс hourly freshness и API usage. Durable checkpoint нужен именно для 1000-item list page: например, 1000 выбранных IDs могут законно прийти в 13 attributes pages (12×75+100), 14 pages (13×75+25) либо 20 pages по 50, затем в столь же разбитых prices/stocks. `20 pages × 1 item` при `total=1000` **не** является успешной страницей: существующий contract завершит её protocol failure после safety cap, и proposal это не расширяет. Публичный `max_pages=1..50` по-прежнему не задаёт physical budget. Уменьшать request `limit` разрешается только при доказанном переполнении измеренного staging/response/performance budget **до** применения этой list page: удалить private checkpoint generation и перечитать с тем же committed run cursor меньшим limit, без изменения прошлых страниц или provider limits.

Предлагается additive private staging: одна `MarketplaceCatalogPageCheckpoint` на `MarketplaceCatalogSync.id` и child rows `MarketplaceCatalogPageItem` с unique `(checkpoint_id, domain, product_id)` и `ON DELETE CASCADE`. Новый nullable private credential/source fingerprint на самом **run** связывает его с account identity: сегодня failed/paused `MarketplaceCatalogSync` можно выбрать по account без такого доказательства. Конкретный существующий источник fingerprint — `services/ozon_account_sync.py::_fingerprint(account)`: SHA-256 от `external_account_id + NUL + credentials_encrypted`; он уже хранится только в private job progress. `credential_version` у `SellerMarketplaceAccount` обозначает формат encryption envelope, а не ротацию ключа, и не годится для этой границы. Смена ciphertext при rewrap того же ключа консервативно начинает новый sweep. Parent checkpoint хранит immutable `seller_id/marketplace_id/account_id`, тот же private fingerprint, run ID, phase/visibility, **входной** list cursor, request limit, generation, нормализованный ordered base list, его hash, provider total и **выходной** cursor. Также хранит текущий domain (`info → attributes → prices → stocks → apply`), cursor/expected total/seen count этого domain, число/размер staged rows и момент первого list observation. Child row хранит только строго нормализованные allowlisted данные, source domain и actual observed-at, без API key, raw response, headers или buyer data. Private checkpoint и run fingerprint не попадают в `BackgroundJob` result, listing serializer или UI. CHECK для stage/неотрицательного размера, unique run и row keys, FK и expiry index проверяет fail-fast миграция; она не переписывает исторические runs/listings.

На каждом tick worker под прежним `ozon-account-sync` file claim, общим account-operation lock и catalog file claim повторно читает exact seller/account, active state и `_fingerprint(account)`. Несовпадение seller/account/marketplace, fingerprint либо run/phase/start cursor останавливает использование staged page. `account.version` может измениться при безвредном label/VAT edit, поэтому **не** является обязательным fence и не сбрасывает продолжение каждой страницы; общий account lock исключает одновременную mutation внутри tick. Ротация/отключение сохраняют нынешний terminal исход job. `force_restart` создаёт новый run и не подхватывает checkpoint старого. Failed/paused run возобновляется только если он остаётся latest **и его persisted run fingerprint совпадает**; completed/newer run его supersedes. Исторический run с `NULL` fingerprint нельзя безопасно связать с текущим ключом: его не backfill-ить по догадке, а начинать новый sweep с пустого cursor, сохранив старый run как историю. При crash после committed page checkpoint уже удалён; следующий tick начинает новый list cursor.

Перед каждым HTTP вызовом ORM session должна быть чистой и без открытой SQLite write transaction. Уже на list response сравнить `total` с committed `run.phase_expected_total`, если он задан, чтобы не тратить enrichment calls на заранее недопустимую страницу. Дальнейшее чтение нормализуется и сверяется с immutable base product-ID/offer-ID set; одна короткая транзакция записывает **и** rows ответа, **и** cursor/total/seen текущего domain. Только после commit начинается следующий HTTP. Crash до этого commit допускает повтор *read* того же domain cursor, но не повторно применённую страницу. Дубли ID между cursor pages, foreign product ID, conflicting offer ID, total drift, пустая промежуточная страница, loop cursor и превышение 20 pages остаются protocol failure. Данные разных credentials, account, run или phase никогда не объединяются. Все domains должны завершиться перед вызовом существующей полной cross-domain проверки и `_apply_catalog_page`; staging cleanup, listing/link changes, counters, phase и run cursor коммитятся **в одной транзакции**. Ошибка flush или link reconciliation откатывает весь apply и сохраняет последний completed snapshot; при terminal malformed checkpoint очищается отдельно после фиксации причины, без partial projection. Temporal snapshot upstream этим не создаётся: это coherent локальная страница из точно проверенных ответов, а не доказательство одновременного состояния Ozon.

## Budget, due, свежесть и пространство

Сохранить существующие 12 start calls/tick, 45 секунд, timeout `3/6`, `read_retries=0`, общий Ozon rate ledger, максимум 8 provider/transient failures и возраст job 24 часа. Достижение локального call/start budget на границе **следующего** вызова завершает tick как normal `pending` с persisted stage и ближайшим due; оно не увеличивает transient failure count. `429` и local rate-limit сохраняют прежний `Retry-After`/due без sleep и без раннего повторного запроса. Один due account получает один bounded slice за tick; очередь продолжает выбирать других готовых продавцов до LIMIT 100, а in-page resume не закрепляет worker или lock между тиками. Если текущая страница ждёт cooldown, её checkpoint остаётся private и другой account может идти дальше.

Локальные storage/TTL gates ещё требуют offline benchmark на реальной форме больших нормализованных страниц; **64 MiB на page generation, 512 MiB на все live checkpoints и 30 минут absolute age** — только кандидаты для измерения, не runtime defaults. При выборе финального cap нормальная 1000-item страница должна оставаться 1000-item, если её фактические bytes/peak memory/elapsed work укладываются в бюджет. После каждого response проверяется нормализованный размер до короткого DB commit; большой отдельный response требует ограниченного размера до JSON decode, иначе staging cap не защищает память. При **глобальном** давлении не начинать новую provider call, дать due другим jobs и возобновить после освобождения места: глобальное давление само по себе не уменьшает page width. Если измеренный **per-page** cap превышен до apply, атомарно отбросить только эту private generation и перечитать тот же committed cursor с `limit 1000 → 500 → 250 → … → 1`; число generations ограничено, а один oversized item даёт явный bounded `invalid_snapshot` без усечения. Локальный call budget и число cursor pages не являются поводом уменьшить list page. При expiry или долгом `Retry-After` discarded staging не применяется: после cooldown перечитать страницу с тем же committed cursor. Повторные expiry учитываются в существующем пределе неуспешных попыток/24h, чтобы перегруженная очередь не перечитывала её бесконечно. Для staged values хранить время реального наблюдения; commit после паузы не должен приписывать раннему ответу более свежий `*_synced_at`. Проверка общего cap и reservation происходят атомарно в SQLite, без записи через HTTP; stale/terminal staging удаляется bounded чанками.

## Совместимость и порядок внедрения

Сохранить один `MarketplaceCatalogSync` как владелец committed cursor/phase и нынешние результаты jobs/API; новые таблицы — только private промежуточное состояние. Вызов `sync_ozon_account(max_pages=1)` из worker продолжает означать максимум **одну завершённую** list page за tick, но теперь может вернуть `paused` с неполной staged page и без увеличения `page_count`. Прямой service caller и существующие normalizers должны использовать тот же staged state machine либо явно остаться изолированным синхронным интерфейсом с тестами на старую семантику; второго пути, который выдаёт budget failure за provider outage, быть не должно. Schema migration — additive после `migrate_add_marketplace_listings.py`, идемпотентная/fail-fast, включённая в Docker entrypoint, прямой startup, scoped и comprehensive runners. Исторические failed/paused runs без доказанной credential identity не возобновляются: новый sweep идёт с пустого cursor, старые строки сохраняются без backfill. Rollback runtime не удаляет таблицы и listings, но старый worker не сможет читать staged page: до возврата старого runtime либо завершить/остановить active catalog jobs, либо ожидать повторных reads с committed cursor; эта граница должна быть явной в release runbook.

Вариант без миграции — list limit **3**: максимум `1+1+3×3=11` calls даже при одном ID на enrichment page. Он сохраняет page atomicity, но превращает 8719 товаров минимум в 2907 тиков на одну phase (более восьми часов при 10 секундах/tick), повышает риск total drift и ломает hourly freshness. Blanket limit 20 тоже даёт минимум 436 list pages/~73 минуты, потому не принят. Повышение лимита до 62 меняет консервативный network budget; сохранение raw pages в `BackgroundJob` делает публичное/частное состояние и размер job непредсказуемыми. Поэтому предлагается bounded normalized staging с обычной 1000-item list page и измеряемым fallback только при реальном переполнении; кандидаты 64/512 MiB/30m принимаются лишь после offline performance и crash tests.

## Матрица проверок до реализации

| Сценарий | Критерий |
| --- | --- |
| 1000-item base page, attributes: 12×75+100, 13×75+25 и 20×50 rows | При 13, 14 или 20 допустимых cursor pages на каждом tick ≤12 calls; job не получает `ozon_read_budget` failure; staged pages не перечитываются; list limit остаётся 1000 и cursor появляется только после всех domains. |
| Каждый из attributes/prices/stocks отдаёт 20×50 rows для 1000 IDs | До 62 calls за несколько due ticks, не более 20 на domain; один atomic apply; totals/identity exact, без автоматического page downshift. |
| Crash перед и после stage commit, перед и после apply commit | Только read может повториться до stage commit; ни одно committed listing/link/counter изменение не повторяется; checkpoint и run cursor согласованы. |
| Instrumented fake transport при создании/resume каждого stage | Перед каждым provider call нет незавершённой SQLite write transaction или autoflush; account/catalog claims действуют только на текущем bounded slice. |
| 429/local limit с long `Retry-After`, restart, TTL expiry | Нет sleep/раннего request; due переживает restart; expired staging отбрасывается без apply, затем свежий list read; 8 failures/24h остаются bounded. |
| Другой seller/account, reconnect/re-encryption, disable, harmless label/VAT version change, force restart, newer completed run | Чужой/устаревший checkpoint не применяется; credential change останавливает прежний job, а label/VAT edit не вызывает бесконечных перечитываний; тот же account lock и last-good каталог. |
| Duplicate/foreign/conflicting IDs, total drift, cursor loop, empty middle page, >20 pages, 20×1 при total=1000, malformed JSON | Terminal protocol failure без partial listing page и без cursor advance; `ALL`/`ARCHIVED` ожидаемое пересечение остаётся допустимым. |
| Normal 1000-item page/8719-item sweep, измеренный per-page overflow, global pressure, huge one item, 30m expiry, 100+ due sellers | Нормальная страница и число list calls сохраняются; page width снижается только по собственному byte/peak/time overflow до apply; глобальный cap даёт due без downshift; один oversized item — явная ошибка; ready seller не голодает. |
| Fresh DB, historical DB, interrupted/repeated migration и old runtime rollback | Constraints/unique/FK/indexes проверены; миграция no-op при повторе, atomic при ошибке; исторические rows не изменены; old runtime читает только committed cursor. |

Все network fixtures должны быть synthetic/offline, включая настоящий `OzonAccountSync` scheduler и `MarketplaceListingService` с моделью SQLite; отдельный нагрузочный прогон измеряет 1000-ID pages, каталог 8719 товаров, candidate 64/512 MiB caps и очередь при 45-секундном tick budget. Эти проверки ещё не выполнены.
