# Дозаполнение карточек по исходным данным и схеме категории

Статус: реализация по запросу владельца от 27.09.2026. В production отдельного seller-facing AI-дозаполнения Ozon пока нет. Этот документ дополняет [план загрузки](../OZON_CARD_UPLOAD_PLAN_2026-09-26.md), а не заменяет его.

## Два независимых результата

1. Администратор обрабатывает недопарсенный общий каталог `SupplierProduct`. Разбор сохраняет источник, проверенные значения, предложения и журнал изменения общей карточки. Он не меняет seller-owned карточки или marketplace listings. Продавец переносит обновления общей карточки существующим явным действием.
2. Продавец по желанию запускает дозаполнение конкретных подготовленных Ozon-черновиков по их выбранной паре category/type. Результат — отдельные предложения; он не пишет в общий каталог, не меняет черновик до принятия продавцом и не публикует его.

`source_prepare` и `reviewed_drafts` остаются независимыми от AI: уже готовые карточки можно просматривать и отправлять, пока остальные обрабатываются. Ожидание модели, 429, отказ модели и отсутствие AI-ключа не блокируют обычное ручное заполнение.

## Модель и профиль

Официальный native model ID — `deepseek-flash`, соответствующий DeepSeek V4.1 Flash. Проверено 27.09.2026 по [списку моделей](https://api-docs.deepseek.com/api/list-models/) и [объявлению DeepSeek от 10.09.2026](https://www.deepseek.com/en/news/deepseek-v4-1-flash/). Старые aliases не закрепляются как актуальные имена. Наличие ключа ещё не доказывает успешный structured parsing; небольшой реальный пилот обязателен до массового прогона.

Нужен отдельный профиль парсинга: native DeepSeek credentials/base URL и `deepseek-flash`, `thinking.type=disabled`, `temperature=0`, ограниченный JSON output, одна физическая попытка на выделенный бюджет. Низкая температура уменьшает вариативность, но не заменяет evidence/native validation и не гарантирует одинаковые ответы. Параметры сверены с [официальным Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/). Не менять остальные orchestration/генеративные профили как побочный эффект. Native model ID нельзя послать с OpenRouter key или наоборот; OpenRouter требует отдельного проверенного model ID и своего профиля. Не делать скрытый fallback между провайдерами или на более дорогую модель.

## Вход и доказательства

- Точный `seller/account/draft/version`, выбранная category/type, свежие определения атрибутов и официальные словари Ozon.
- Только разрешённые исходные факты товара с неизменяемым source fingerprint. Уже заполненные значения передаются как ограничения: модель предлагает дополнения только к пропускам.
- `MarketplaceFactPackBuilder.unverified_suggestions`, старые `ai_*` и чужие карточки не являются доказательством. Source-only fingerprint должен исключать сам результат модели, иначе сохранение предложения запускает бесконечное устаревание.
- Каждый кандидат содержит exact attribute/complex identity, typed value или dictionary ID, evidence path и буквальную цитату. Python проверяет их самостоятельно. Source и seller text передаются как данные, не как инструкции модели.
- Семантические нормализации, если разрешены закрытым правилом, помечаются отдельно; confidence модели не доказывает факт. Нельзя угадывать массу/габариты упаковки, состав, страну, возраст, сертификаты, ТН ВЭД или маркировку. Явно наблюдённый факт допускается только с соответствующей единицей/областью значения.
- Не передавать цены, остатки, ключи, покупательские данные и произвольный raw JSON. Не дополнять штрихкоды/медиа/коммерческие условия.

## Программная проверка и принятие

Проверяются exact-set IDs, JSON shape/size, тип значения, единицы, диапазоны, cardinality/collection, scope complex group, fresh dictionary membership, evidence/числовые границы, отсутствие перезаписи заполненного значения и запрещённых полей. Неверный ответ не становится черновиком; повтор не является способом обойти проверку.

Первая реализация дополняет простые строковые и словарные характеристики. Составные группы, измерения и регулируемые сведения остаются для ручной проверки; расширение требует отдельной приёмки нативной валидации.

Сохраняются отдельные run/item/suggestion records с исходным fingerprint, draft version, category/type/schema/dictionary fingerprint, запрошенной моделью, временем, числом попыток и usage. Перед записью результата перечитываются актуальные fingerprints. Изменившийся товар или схема дают `stale` и требуют нового запроса; текст запоздавшего ответа отбрасывается, сохраняются только безопасный статус и usage.

Продавец видит `Сейчас → Предложение`, источник и причину, может принять отдельные значения или отклонить их. Apply принимает exact suggestion IDs + current expected draft version, повторяет source/reference gates и полную валидацию. Частично заполненный complex group нельзя применить как валидную полную группу. Принятый diff и reviewer сохраняются. После принятия версия черновика меняется, прежний просмотр для отправки перестаёт действовать.

## Фоновая обработка и скорость

- HTTP только принимает bounded exact selection и ставит durable job; ни LLM, ни Ozon schema fetching не выполняются в запросе браузера.
- Детерминированное заполнение из фактов и уже валидированных результатов выполняется первым. Один fresh source/type/schema/model fingerprint переиспользуется, пока не изменились существенные данные.
- Стартовый бюджет: до 200 черновиков/run, до 6 совместимых товаров в одном schema-specific chunk, 3 одновременных LLM calls глобально для parsing lane, не более 2 одного seller. Эти границы реализованы и проверены на синтетических данных; production-приёмка остаётся отдельным этапом.
- Перед запуском futures резервируются физические попытки и token budgets; отдельные provider clients выполняют только HTTP. ORM работает в одном coordinator-потоке короткими транзакциями, без SQLite write lock через HTTP.
- Shared limiter распространяется на admin и seller parsing lanes; увеличение web workers не увеличивает бюджет. Durable due/cooldown на 429; никаких sleep или бесконечных retries внутри scheduler.
- Отмена прекращает выдачу новых chunks; уже полученный результат не применяется после отмены. Restart, двойной POST, потеря ответа браузером и истёкший lease не дублируют обработку/применение.
- System instructions, output schema и category reference prefix стабильны и идут до динамических source facts. Сохраняются API requests, input/output/cache-hit/cache-miss/reasoning tokens; неизвестная стоимость не показывается нулевой. Provider-reported и estimated cost различаются.

## UX

В подготовке — необязательное действие «Предложить недостающие характеристики». Перед запуском видны количество товаров, использование настроенного AI-провайдера и доступный бюджет. Статусы отдельно от готовности публикации: «В очереди», «ИИ обрабатывает», «Предложения готовы», «Нужно заполнить вручную», «Исходные данные изменились», «Отменено».

В редакторе — подсветка предложенных и принятых значений, фильтр «Дополнено ИИ», счётчик принятых/ожидающих/отклонённых. Цвет сопровождается подписью/иконкой, source evidence доступно с клавиатуры. Ошибка сохраняет ручной ввод и выбранные предложения. Мобильные 320/390, обе темы, focus/keyboard и длинные названия характеристик входят в browser gates. Неработающие AI-кнопки в UI не выкатываются.

## Очередность и приёмка

Read-only inventory 27.09 в 00:30 МСК: 21 948 общих товаров двух поставщиков, у всех есть source snapshot. У 12 131 нет legacy `ai_parsed_at`; у 10 264 нет `ai_marketplace_json`. Это разные признаки, ни один не означает точный backlog подтверждённых актуальных характеристик. Активных admin enrichment runs в момент чтения нет. Exact pilot/остаток выбираются после source/schema freshness проверки.

Аудит обнаружил, что прежний `_product_source` admin enrichment использует нормализованные колонки, которые могли изменяться старым AI parser. До реального прогона новый Flash путь обязан брать whitelist исходного snapshot, иначе AI-вывод мог бы стать доказательством сам для себя. Старые start POST переводятся в typed 409 со ссылкой на проверку выбора в Flash. История старых задач сохраняется; выбранные ID и фильтры повторно проверяются перед запуском нового процесса. Перевод кнопок проходит отдельную приёмку.

1. Зафиксировать точную настройку admin parsing, модель и агрегированный backlog недопарсенных supplier rows; не считать любое старое AI-поле успешным текущим разбором.
2. Ввести task-specific Flash profile и unit/transport checks без сети. Пилот до 12 разных карточек: проверить 100% предложений, токены, latency, словари, пропуски и evidence. Затем волна до 60 и дальнейшие возобновляемые волны до 200, только при успешных предыдущих gates. Сохранить exact manifest, не затереть принятые текущие результаты.
3. Реализовать seller durable suggestions и apply через существующий draft update/validation boundary.
4. Подключить Vue review и независимую публикацию готовой части.
5. Проверить tenant isolation, source/schema/dictionary/version drift, конфликт ручного ввода, дубликаты/чужие IDs, выдуманные evidence, complex attributes, истечение lease, restart, cancel, lost response, 429, лимиты памяти/токенов/конкурентности и reuse.
6. Реальный API пилот проверяет парсинг отдельно от публикации. Успешная локальная валидация/AI не доказывает загрузку или прохождение модерации Ozon; для reviewed card upload нужны собственные provider result/readback gates.
