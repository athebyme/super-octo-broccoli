# Интеграция Ozon: состояние и план

Актуально на **30.09.2026**. Это статус реализации и проверок, а не заявление о завершённом запуске Ozon. UX-01 и исправление повторных startup-миграций перенесены в `main` по [handoff](docs/operations/2026-09-30-ux-01-main-handoff.md) вместе с текущей интеграцией. В 20:02 UTC host watcher автоматически пересобрал чистый локальный `main`: production работает на образе `sha256:1b920bfc88c36373c6579e5287a2753176c3c3eb9a77b5460bedb5c3a6f57daa`. Внутри него точный source manifest прошёл 1209/1209; контейнер healthy, heartbeat scheduler живой. Причина лишнего deployment — старый watcher принял отстающий remote за новый коммит. Исправленный host watcher перезапущен и проверен: при отстающем remote он не запускал build. Объединённый `main` опубликован в `origin/main` fast-forward. Принятая локальная копия БД датирована 26.09 и считается устаревшей; владелец отменил создание новой копии для предыдущего передеплоя. Внешнее хранилище бэкапов пока не подключается.

## Цель

Продавец проходит целостный путь в Vue: подключает Ozon, выбирает товары и категории, видит требования площадки и фотографии, исправляет карточки, по желанию получает проверяемые AI-предложения для пустых характеристик, принимает нужные значения, отправляет готовые карточки и видит достоверный результат Ozon. Сбой, квота, изменение исходных данных или неопределённый ответ не превращаются в ложный успех или повторную запись. Контракты Wildberries и существующие данные сохраняются.

## Что реализовано

- Аккаунт Ozon, чтение каталога, категорий и справочников, seller-scoped черновики, контроль качества, очереди пакетной загрузки, журнал операций и readback. Подготовка и отправка разделены: неготовые карточки не блокируют готовые.
- Vue-интерфейс выбора и подготовки с разными категориями, обязательными характеристиками и словарями, фотографиями, явными состояниями загрузки и ошибок, адаптивными desktop/mobile видами и светлой/тёмной темой. UX-01 объединил переходы между рабочими экранами; [карта действий](docs/design/ux-01-action-map.md) и [результат](docs/design/ux-01-implementation.md) описывают конкретные сценарии.
- Native `deepseek-flash` для административного разбора каталога и опционального дополнения Ozon-черновиков. Предложения основаны на исходных фактах и актуальной схеме категории, показывают подтверждение из источника и применяются только после выбора продавца. Цена, остатки, медиа, габариты и сложные группы автоматически не генерируются. Общий durable бюджет и ограниченная параллельность не задерживают отправку уже готовых карточек.
- Ограничители запросов Ozon, quarantine для неизвестного результата записи, защищённое сравнение полного состава карточки и фотографий после импорта. Строгий readback пока сравнивает URL медиа буквально; реальный Ozon может вернуть другой CDN URL, и это требует отдельного наблюдения до любого изменения критерия.
- Пошаговый startup journal: 79 удостоверенных шагов повторно не выполняются при том же коде и схеме; неизвестный drift останавливает запуск. План уже содержит все Ozon-миграции текущего исходного дерева, включая compliance, загрузку и очереди чтения. Операционный контур рассылает редкие статусы всем активным подписчикам Telegram-бота, написавшим `/start`.

## Что подтверждено

- Объединённый `main` прошёл полный изолированный UX gate: 6/6 этапов, 109 тестов и 493 проверки макетов. Полный Ozon gate прошёл 12/12 этапов: 2409 контрактных тестов, 93 браузерные проверки и 444 проверки макетов, без provider-запросов. Это synthetic `network=none` приёмка, а не реальная публикация товара.
- Startup-исправление прошло 42 focused теста и первый/повторный 79-шаговый запуск на пустой SQLite в изолированном image. Production перешёл с предыдущего verified journal за 1,262 секунды; 79 receipts подтверждены. На объединённом `main` дополнительно прошли 57 тестов и 7 подтестов startup/маршрутов, а также 96 тестов и 58 подтестов UX/Ozon. Исходники migration plan и fingerprints совпали с заверенным receipt; добавлять новые шаги не требуется.
- Сверка 1210 путей исходного манифеста startup-выпуска с объединённым `main` обнаружила только изменения в `AGENTS.md`, этом статусе, документе цен, двух текстах лицензий шрифтов и отсутствие одноразового release-helper. Runtime, миграции, UI и тесты по остальным путям совпали на момент первой публикации. Выпущенный объединённый образ содержит manifest 1209 файлов с aggregate `2c657df0c6ee59875287b9e84e3b1cec0018edbab742d71a5011eb88fc1284bc`; он проверен внутри production image и до/после обоих offline gate. После него в `main` изменены статус, AGENTS, host watcher/test и узкая AI-диагностика/тест; UI и миграции не менялись. Текущий source manifest в репозитории отражает новую версию отдельно от работающего образа.
- Read-only production-проверка фото подтвердила один уже кэшированный source preview в редакторе: `200 image/jpeg`, JPEG 1200×1200, без изменения cache file. Отдельный exact URL из наблюдённого Ozon listing на разрешённом публичном CDN вернул JPEG 1200×1200 без credentials и redirects. Это точечное доказательство доставки изображений, не массовая проверка всех 8719 карточек.
- Живой seller-scoped browser smoke после окончания Vue-загрузки увидел 12 настоящих карточек каталога (0 skeleton), 12 `src` для изображений, два редактора с разными типами и категориями и 11 элементами характеристик. Каталог, категории, фасеты, оба черновика и editor API ответили 200; на 1440/390 px нет горизонтального переполнения, JS-исключений и заблокированных write-запросов. Проверка заменяла внешние изображения тестовым пикселем и перехватывала photo proxy; итоговый browser media gate остаётся неполным. Два подписанных локальных image-запроса возникали позже на страницах черновиков, но их ответ в bounded smoke не был наблюдён, поэтому этот прогон не доказывает их декодирование.
- Отдельный ограниченный browser media probe без плейсхолдеров взял два exact изображения каталога с публичного Ozon CDN (`GET 200`, без credentials/redirects) и подал их реальные байты в Chromium: оба декодировались (`naturalWidth > 0`). На двух editor routes и их data API получены 200; одно заранее подтверждённое cache-hit source фото декодировалось в preview. Другой выбранный source имел cache miss; все photo-proxy запросы перехвачены до Flask, поэтому холодная очередь/pending path этим тестом не проверены. JS-ошибок и write-запросов не было. В отдельной прямой проверке ранее локальный cache-hit photo route ответил JPEG 1200×1200.
- Новый переданный ключ Ozon использовался только в памяти: `/v1/roles` вернул 200 с нужными разрешениями, `/v3/product/list` подтвердил собственный товар. Один запрос `/v1/product/prices/details` по подтверждённому SKU вернул 403 с не-JSON ответом. Ключ не сохранён в production-аккаунте, записей через него не было. Причина 403 неизвестна; покупательская цена и скидка площадки остаются неизвестными. [Ценовой контракт](docs/design/ozon-prices.md) не смешивает их с seller `price` и `old_price`.
- Конфигурация production собирает нативный seller DeepSeek Flash профиль: модель `deepseek-flash`, один physical attempt, выключенное логирование payload. Точечный pilot на трёх разных seller-owned черновиках выполнил ровно по одному native-вызову на каждый: все HTTP 200, суммарно 3300 входных и 300 выходных токенов, latency около 10 секунд на вызов. Первый результат — `no_evidence`, два следующих — `no_evidence` с безопасным кодом `ai_fields_rejected`. Validator не создал ни одного предложения; review/apply не выполнялись, версии черновиков не изменились. Provider cost и оценочная стоимость в ledger отсутствуют: это неизвестно, а не ноль. Массовый запуск пока не принят.
- Исправление диагностики Flash в `main` сохраняет только один разрешённый код основной причины отклонения на карточку и пересчитывает устойчивый агрегат по запускам из сохранённых строк. Существующие seller-facing item codes остаются общими, исходные значения/цитаты и raw model response не записываются. Повторная локальная приёмка: 40 тестов и 12 подтестов. Причины прежних двух ответов восстановить нельзя; новый код ещё не развёрнут и требует нового малого pilot.
- Исправленный `scripts/autodeploy.sh` прошёл 23 целевых теста и `bash -n`. Host service перезапущен; `--once` на живом checkout показал `local e3feaa0, remote a9e95b2 → deferred`, а production image/start time остались прежними. В рассылку был отправлен корректирующий статус 2/2 активным подписчикам `/start`.
- Перед следующим развёртыванием 30.09 в 20:44–20:53 UTC сделана свежая локальная проверенная копия production SQLite: 13 970 239 488 байт исходной БД, gzip 1 826 935 144 байта, фактическое отдельное восстановление, совпадение SHA и `quick_check=ok`. Manifest и архив находятся только в приватном `/app/data/backups/`; внешнее хранилище не подключалось.

## Что сейчас проверяется

1. Довести production browser media gate до холодного photo-proxy/pending пути и проверить обычный login flow. Точечное декодирование настоящих CDN и cache-hit изображений подтверждено, но browser smoke использовал точную signed seller session только для read-only запросов; сценарий обычного ввода логина и декодирование всех изображений каталога не подтверждены.
2. Подготовить ограниченный реальный пилот загрузки одной проверенной карточки. Сохранённые 20 черновиков не дают готовой партии: 18 `blocked/invalid`, один `needs_category/invalid`, единственный `ready/valid` проверялся 25 июля. Read-only аудит не нашёл ни одного кандидата со всеми подтверждёнными полями: source-observed размеры упаковки 0/20, допустимый VAT 0/20, обязательные compliance-атрибуты 0/20; defaults и complete marking registry тоже пусты. Scheduler heartbeat healthy, две старые uncertain операции product-scoped, account-wide quarantine нет. Нужны подтверждённые продавцом размеры/НДС/compliance, свежий seller review, затем один import task, результат модерации и `/pictures/info`. При неопределённом результате повторную запись не отправлять автоматически. Сохранить существующие флаги (`auto-publish=0`, commercial writes=1) и общий ledger.
3. После развёртывания безопасной диагностики провести новый ограниченный Flash pilot и прочитать агрегат причин отклонения без raw model response и исходных значений. Проверить достаточность source-only evidence и вручную просмотреть хотя бы одно принятое предложение. Только после успешной малой партии расширять обработку неполного каталога волнами, сохраняя seller review, общий бюджет и source-only grounding.

## Что остаётся открытым до полноценного выпуска

- Реальный сквозной путь продавца: выбор товара → проверка разных категорий и характеристик → фото → подготовка → отправка → task/readback → видимость и статус карточки. Отдельно проверить ошибки, 429, частичный результат, повторное открытие, desktop/mobile и обе темы.
- Подтверждённый источник базовой цены до всех скидок, покупательской цены и скидки Ozon. Официальные названия кабинета не дают exact mapping к полям Seller API; до проверки собственного SKU неизвестные значения остаются неизвестными.
- Для каждого следующего крупного deployment сверять свежесть принятого локального backup и реальную возможность восстановления; внешнее хранилище пока не требуется.
- Объединённый runtime `main` уже работает в production из-за автоматического пересоздания. Последние статусные документы и host watcher fix опубликованы в `origin/main`, а новая AI-диагностика пока только в локальном `main`; они не входят в запущенный app image. Host watcher исполняет исправленный скрипт без нового пересоздания приложения. Для следующего deployment уже принят свежий локальный backup/restore rehearsal; остаётся подтвердить точный image/source evidence. О результатах значимых этапов сообщать в Telegram всем активным `/start` подписчикам без частой рассылки.
